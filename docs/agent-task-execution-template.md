## Prepared `/moda-task` fast path

When the packet contains:

```json
"prepared_execution": true
```

then the launcher has already completed the mechanical startup contract for this
attempt. In particular it has already:

- resolved the canonical **primary** workspace rather than treating a previous
  task worktree as the workspace root;
- derived the parent and implementation worktree paths solely from that
  canonical workspace plus `<TASK_ID>`;
- created or reused the exact dedicated parent task worktree;
- fetched/pruned and synchronized its `task/<TASK_ID>` branch;
- read the authoritative task definition from the synchronized parent worktree;
- verified `execution_mode: agent`, `status: ready`, assigned agent and every
  explicit `depends_on` task;
- created or reused the exact dedicated implementation worktree;
- fetched/pruned and synchronized its `task/<TASK_ID>` branch;
- run, in the implementation worktree:

  ```bash
  git submodule sync --recursive
  git submodule update --init --recursive
  ```

- verified recursive submodules are initialized at the exact recorded commits;
- re-synchronized/re-read the parent task immediately before claiming;
- changed the task to `in_progress`, incremented `attempt`, recorded the
  normalized executor and timestamp;
- committed and pushed the parent claim so it is durable.

**Do not repeat those actions.** In particular, do not rediscover the task,
rerun dependency discovery, create/re-name worktrees, synchronize branches,
initialize submodules again merely as a startup ritual, or claim the task again.
The expected task state when you receive a prepared packet is already:

```text
status: in_progress
executor: <the packet's claim.executor>
```

If the packet does not say `prepared_execution: true`, do not begin repository
implementation from this prompt. Return to the deterministic `/moda-task`
preparation path instead of reconstructing startup manually.

## Required first reads after prepared handoff

The expensive workflow discovery phase is intentionally finished. Start with
implementation context, not launcher context.

1. Read the complete current task file from:

   ```text
   <PARENT_WORKTREE>/<TASK_FILE>
   ```

2. Read documents the task explicitly identifies as `Read first`.
3. Read an interface/contract document only when the task requires that contract
   to implement the bounded change.
4. Do **not** read dependency task files merely to re-prove dependency status;
   the launcher's explicit dependency gate already did that.
5. Do **not** automatically reread generic workflow policies, the development
   baseline, workspace doctor output, or unrelated architecture/task files.

The task document remains authoritative for scope, Work Items, Acceptance
Criteria, Validation, dependencies and cross-repository contracts.

## Implementation boundary

All implementation work must occur only in:

```text
<IMPLEMENTATION_WORKTREE>
```

`<REPOSITORY_PATH>` is a source/reference checkout used by the launcher for Git
worktree registration. It is **not** an authorized task implementation checkout.

Do not switch a shared/default checkout or another task's worktree. Do not derive
another worktree path from the current directory. Do not append this task ID to a
previous task worktree name.

Implement only the current task's bounded repository-owned scope. If the task
requires a change owned by another repository, stop that part and return the
cross-repository requirement to `moda_architect`.

## Lean environment rule

Use the environment already available. Before the first Node-related command:

```bash
command -v node >/dev/null 2>&1 || \
  source "<WORKSPACE_ROOT>/scripts/bootstrap-node.sh"
```

The workspace doctor is **not** part of normal `/moda-task` startup. Run it only
when one of these conditions actually applies:

- a real environment/dependency problem occurs;
- the current task changes relevant Node/toolchain/dependency/configuration;
- the task Validation section explicitly requires it;
- `moda_architect` explicitly requests it;
- observed behaviour materially contradicts the known development baseline.

Do not rediscover known baseline conditions or Zod state during an unrelated
healthy task.

## Validation

Use the task's `## Validation` section as the primary validation contract.
Before repository validation, inspect the implementation repository's actual
`package.json`/declared scripts rather than assuming scripts are uniform across
repositories.

Run focused validation first. Run broader validation only when the task requires
it or it is necessary to establish that the task introduced no regression.
Document known baseline failures by their existing baseline ID when applicable;
do not reinvestigate them automatically.

## Git / VCS after prepared claim

The claim is already committed/pushed by the launcher. Do not create another
claim commit.

For implementation work:

- stay on `<TASK_BRANCH>` in `<IMPLEMENTATION_WORKTREE>`;
- stage only files belonging to this task;
- commit and push the implementation branch;
- never merge the task branch into `main`;
- never push directly to `main`;
- never force-push unless the developer explicitly authorizes that exact action.

For the parent task report:

- edit only `<TASK_FILE>` (plus an explicitly task-owned evidence artifact if the
  task itself authorizes one);
- do not stage a changed implementation submodule gitlink;
- record the launcher-provided physical worktree/synchronization/submodule
  evidence from the preparation packet;
- set the task/report to review-ready according to the normal task lifecycle;
- commit and push the parent `<TASK_BRANCH>`;
- stop at `review` for `moda_architect`.

The developer owns final merges and updates to `main`.

## Stop conditions

Stop and return concrete evidence instead of improvising when:

- the prepared task ID does not match the task file;
- the implementation worktree is no longer the packet's exact canonical path;
- another task's worktree/branch appears to be in use;
- a new cross-repository requirement changes architecture/scope;
- validation reveals a task-introduced regression you cannot resolve within
  scope;
- a task-specific contract conflicts with repository ownership or architecture.

Otherwise, proceed directly from the required task/context reads to source
inspection, implementation and validation.
