# Persist capability releases and conversation tool grants

## Architecture

Architecture ID: ARCH-020.

Architecture document: docs/architecture/ARCH-020-commerce-agent-studio-mcp-capabilities.md.

Coordinator: moda_architect. Read the complete parent architecture and relevant dependency/contract tasks. Execution handoff: docs/architecture/ARCH-020-implementation-handoff.md.

## Objective

Provide durable versioned capability publication and conversation-wide immutable tool grants.

## Context

Merchant-selected capabilities should drive WhatsApp CommerceAgent behaviour through a separate Next.js MCP server with a team-only Studio. Production conversation admission, ordering, model hosting and delivery remain in Background. This is a pre-production breaking rollout, with no implicit permission to delete durable data.

Task definition is on local workspace main by the developer's explicit 2026-09-20 review request. It is not a claim, task-branch materialisation or implementation approval. All execution fields remain unclaimed.

## Scope

Canonical prisma/schema.prisma, one additive migration, the two named validation scripts/package commands below, schema/migration fixtures and generated ERD only. No application implementation.

## Out of Scope

Other repositories' implementation, unrelated refactoring, automatic execution of enabled tasks, live deployment, main integration/push and changes to billing prices/merchant entitlements. No cart/order/discount mutation, WhatsApp sending from Commerce, arbitrary executable code or arbitrary-host HTTP endpoints; C14 validated read-only GraphQL definitions are explicitly permitted. No duplicate discount catalogue/merchant configuration system. Shared indexes and architecture reconciliation remain architect-owned.

## Requirements

ARCH-020 supports only WhatsApp conversations associated with an existing CheckoutRecovery. Enforce Conversation -> CheckoutRecovery -> Shop ownership. Do not create or support standalone conversation grants. This does not authorise deletion or restructuring of pre-existing platform conversation rows.

Follow the parent architecture's tenant/policy/revision contracts and the assigned logical owner. Preserve unrelated changes. Read repository-local AGENTS.md if present. Commerce consumes the canonical database through its nested database/ Git submodule; schema and migrations belong to moda_database. For consumers, use actual accepted and published dependency revisions, not copied task snapshots or hypothetical versions.

### Binding schema contract

Tool definition example and exact execution/template grammar:
[C14: database-defined tools](../../../architecture/ARCH-020-implementation-contracts.md#c14-database-defined-tools-and-response-templates).
The nine-table layout includes independent CommerceTool/CommerceToolRevision
records. Capability revisions pin those tools through toolBindings; the owning
capability supplies the existing Admin Feature mapping.

Implement exactly the nine Prisma models and physical PostgreSQL tables below,
all in the existing `commerce` schema (`@@schema("commerce")`). Keep the exact
model/column names. Do not create a new database or schema, rename these models,
substitute a single generic JSON table, or add a second authentication model.
If implementation reveals a conflict, return it to moda_architect before changing
this contract. Relation-field names may follow repository conventions; physical
columns, types, invariants and deletion behaviour may not vary.

Notation: `String/Text` means Prisma `String @db.Text`; optional means Prisma `?`
and SQL NULL allowed. All other fields are required. IDs use `String @id
@default(cuid())` backed by PostgreSQL text, matching existing model conventions;
`cuid()` is generated by Prisma, not a PostgreSQL default. All timestamps use
`DateTime @db.Timestamptz(3)`. `createdAt` defaults to `now()`; `updatedAt` uses
`@default(now()) @updatedAt`. JSON uses Prisma `Json @db.JsonB`.

Add these enums in `commerce`, with exactly these values:

| Enum | Values |
|---|---|
| `CommerceCapabilitySelectionBinding` | `BASE`, `FEATURE`, `RECOVERY_POLICY` |
| `CommerceCapabilityRevisionStatus` | `DRAFT`, `PUBLISHED` |

### 1. CommerceCapability

| Column | Prisma / SQL type | Null/default | Constraint / meaning |
|---|---|---|---|
| `id` | String / text | cuid | Primary key |
| `key` | String / varchar(128) | Required | Unique; regex `^[a-z][a-z0-9_]{0,127}$` |
| `displayName` | String / varchar(255) | Required | Non-blank |
| `description` | String / text | Optional | At most 4,000 characters |
| `selectionBinding` | CommerceCapabilitySelectionBinding | Required | Selection mechanism |
| `featureId` | String / text | Optional | FK to existing `billing.Feature.id` |
| `enabled` | Boolean / boolean | true | Emergency disable; not a merchant preference |
| `createdAt` | DateTime / timestamptz(3) | now | Created time |
| `updatedAt` | DateTime / timestamptz(3) | now / updatedAt | Last metadata/state edit |

Require `featureId IS NOT NULL` if and only if binding is `FEATURE`. Permit only
one `BASE` row (partial unique index on selectionBinding where BASE). In v1 the
only RECOVERY_POLICY capability key is `discount_assistance`; enforce that CHECK.
The base key is `conversation_core`; enforce BASE implies that key and that key
implies BASE. Multiple feature-bound capabilities may reference the same Feature.
The logical selection identity (`key`, `selectionBinding`, `featureId`) is
immutable once any revision exists; a database trigger rejects a change. Display
metadata and `enabled` remain editable, with audit handled by Commerce.

Indexes: unique key; `(featureId)`. Feature FK: ON DELETE RESTRICT, ON UPDATE
RESTRICT. Do not seed these rows in the schema migration; initial publication
is the explicit COMMERCE-003 operation.

### 2. CommerceCapabilityRevision

| Column | Prisma / SQL type | Null/default | Constraint / meaning |
|---|---|---|---|
| `id` | String / text | cuid | Primary key |
| `capabilityId` | String / text | Required | FK to CommerceCapability |
| `revisionNumber` | Int / integer | Required | Greater than zero; scoped to capability |
| `status` | CommerceCapabilityRevisionStatus | DRAFT | Publication state |
| `promptTemplate` | String / text | Required | 1–32,000 characters; non-blank |
| `configuration` | Json / jsonb | `{}` | JSON object; at most 16,384 bytes of PostgreSQL text representation |
| `toolBindings` | Json / jsonb | `[]` | Array of at most 32 exact {toolId,toolRevisionId} bindings; at most 16,384 bytes |
| `contractVersion` | String / varchar(64) | Required | Non-blank; service validates supported version |
| `editVersion` | Int / integer | 0 | Non-negative optimistic concurrency token |
| `contentHash` | String / varchar(64) | Optional | Lower-case SHA-256 hex; required only on publication |
| `createdByAdminId` | String / text | Required | FK to existing public.PlatformAdmin |
| `publishedByAdminId` | String / text | Optional | FK to existing public.PlatformAdmin |
| `createdAt` | DateTime / timestamptz(3) | now | Created time |
| `updatedAt` | DateTime / timestamptz(3) | now / updatedAt | Last draft edit/publication |
| `publishedAt` | DateTime / timestamptz(3) | Optional | Publication time |

Unique `(capabilityId, revisionNumber)` and unique `(id, capabilityId)` for the
composite membership FK. Index `(capabilityId, status, revisionNumber)`.
All three FKs use ON DELETE RESTRICT / ON UPDATE RESTRICT.

DRAFT requires `publishedByAdminId`, `publishedAt`, `contentHash` all NULL.
PUBLISHED requires all three non-NULL, valid hash and `publishedAt >= createdAt`.
Database trigger rejects UPDATE or DELETE of an already-PUBLISHED row, including
status reversal. The only publication transition is DRAFT -> PUBLISHED. Ordinary
draft changes must advance `editVersion` by exactly one using a service CAS update;
the database trigger checks the increment for every UPDATE. Publication performs
that same increment. The creator and revision identity remain immutable.

Each toolBindings element contains exactly toolId and toolRevisionId, nonempty
strings<=128. SQL enforces array type, max32 items, <=16384 bytes, unique toolId
and object keys/types. A trigger resolves each revision to its named tool and
requires PUBLISHED status on every insert/update, including drafts. This is a
JSON reference enforced by trigger, not a claimed native FK. Published tool
revisions cannot be deleted, so bindings cannot dangle. Empty bindings are valid
for prompt-only capabilities and conversation_core. Publication freezes bindings
with the capability revision. Tool association edits advance editVersion exactly
once with the enclosing draft edit.

### 3. CommerceRelease

| Column | Prisma / SQL type | Null/default | Constraint / meaning |
|---|---|---|---|
| `id` | String / text | cuid | Primary key |
| `releaseNumber` | Int / integer | autoincrement() | Unique positive number; sequence gaps are allowed |
| `responseContract` | Json / jsonb | Required, no default | C16 strict response.v1 definition; immutable with release |
| `responseContractHash` | String / varchar(64) | Required, no default | C16 canonical SHA-256; SQL CHECK lowercase 64 hexadecimal characters |
| `description` | String / text | Optional | At most 4,000 characters |
| `runnerCompatibility` | String / varchar(128) | Required | Non-blank SemVer range, validated by publishing service |
| `contractVersion` | String / varchar(64) | Required | Non-blank supported contract version |
| `createdByAdminId` | String / text | Required | FK to existing public.PlatformAdmin |
| `createdAt` | DateTime / timestamptz(3) | now | Created time |

Unique releaseNumber; index `(createdAt, id)`. Admin FK uses RESTRICT on delete
and update. A release is a completed immutable bundle, not a draft editor: its
row and membership are created in one publishing transaction. Database rejects
UPDATE of release rows. No release removal/garbage-collection API is in v1;
referenced releases are protected by RESTRICT FKs. See the enforcement matrix
for membership assembly, validation and immutability responsibilities.

### 4. CommerceReleaseCapability

| Column | Prisma / SQL type | Null/default | Constraint / meaning |
|---|---|---|---|
| `releaseId` | String / text | Required | FK to CommerceRelease |
| `capabilityId` | String / text | Required | Capability identity |
| `capabilityRevisionId` | String / text | Required | Exact published revision |
| `position` | Int / integer | Required | Non-negative; deterministic prompt order |

Composite primary key `(releaseId, capabilityId)`; unique `(releaseId, position)`;
index `(capabilityRevisionId, capabilityId)`. Use a composite FK
`(capabilityRevisionId, capabilityId)` -> CommerceCapabilityRevision `(id,
capabilityId)`, ensuring the revision belongs to the named capability. All FKs
use RESTRICT on delete/update. No surrogate id or independently mutable prompt.

Database trigger rejects membership referring to a DRAFT revision. Database
rejects member UPDATE and DELETE; this v1 does not garbage-collect releases.
The publishing service creates a release with 1–32 members in a single
transaction, with unique contiguous positions starting at zero, exactly one
conversation_core member, and compatible contracts/tools. It exposes no API to
append members to an existing release. A release-pointer or conversation-grant insert
must validate nonempty membership in the database, so empty partial bundles
cannot become active or be used by a turn.

Release-member insert trigger verifies no existing member in the same release
binds a different toolRevisionId for an already referenced toolId. Equal revisions
are allowed. Capability toolBindings refer to immutable published tool revisions,
so this check remains valid after publication. The service still owns atomic
initial membership assembly and rejects additions to an existing release.

| Column | Prisma / SQL type | Null/default | Constraint / meaning |
|---|---|---|---|
| `environment` | CommerceEnvironment | Required | Primary key; one pointer per environment |
| `releaseId` | String / text | Required | FK to immutable CommerceRelease |
| `editVersion` | Int / integer | 0 | Non-negative; exactly +1 on each update |
| `updatedByAdminId` | String / text | Required | FK to existing public.PlatformAdmin |
| `updatedAt` | DateTime / timestamptz(3) | now / updatedAt | Activation or rollback time |

Index `(releaseId)`. Both FKs use RESTRICT on delete/update. A database trigger
requires a nonempty release and validates editVersion increments; Commerce
performs compare-and-swap using the caller's expected editVersion. Publish and
rollback update this row plus the audit event in one transaction. Rollback never
rewrites a release/revision. No empty/default pointer row is seeded by migration.

| Column | Prisma / SQL type | Null/default | Constraint / meaning |
|---|---|---|---|
| `id` | String / text | cuid | Primary key |
| `actorAdminId` | String / text | Required | FK to existing public.PlatformAdmin |
| `action` | CommerceAuditAction | Required | Exact action enum above |
| `capabilityId` | String / text | Optional | FK to CommerceCapability |
| `revisionId` | String / text | Optional | FK to CommerceCapabilityRevision |
| `releaseId` | String / text | Optional | FK to CommerceRelease |

| `toolRevisionId` | String / text | Optional | FK to CommerceToolRevision |
| `environment` | CommerceEnvironment | Optional | Required for activate/rollback |
| `reason` | String / varchar(1000) | Required | Non-blank; may be a bounded generated reason for draft saves |
| `metadata` | Json / jsonb | `{}` | Object, at most 8,192 bytes; IDs/hashes/change codes only |
| `createdAt` | DateTime / timestamptz(3) | now | Event time |

All FKs use RESTRICT on delete/update. Database trigger rejects audit UPDATE and
DELETE. Indexes: `(createdAt, id)`, `(capabilityId, createdAt, id)`,
`(releaseId, createdAt, id)`, `(actorAdminId, createdAt, id)`,
`(toolId, createdAt, id)`.

Action targets: CREATE_CAPABILITY/UPDATE_CAPABILITY/ENABLE_CAPABILITY/
DISABLE_CAPABILITY require capabilityId. CREATE_DRAFT/UPDATE_DRAFT/
PUBLISH_REVISION require capabilityId and revisionId. CREATE_RELEASE requires
releaseId. ACTIVATE_RELEASE/ROLLBACK_RELEASE require releaseId and environment.
CREATE_TOOL/UPDATE_TOOL/ENABLE_TOOL/DISABLE_TOOL require toolId;
CREATE_TOOL_DRAFT/UPDATE_TOOL_DRAFT/PUBLISH_TOOL_REVISION require toolId and
toolRevisionId. Triggers verify toolRevisionId belongs to toolId.
Database CHECKs enforce required targets; a trigger checks revisionId belongs
to capabilityId when both are present. Fields not required by the action may be
NULL; do not force unrelated links. Never store credentials, prompt text,
customer messages, email/phone or complete provider payloads in audit metadata.

### 7. CommerceConversationGrant

| Column | Prisma / SQL type | Null/default | Constraint / meaning |
|---|---|---|---|
| `id` | String / text | cuid | Primary key |
| `shopId` | String / text | Required | FK to existing commerce.Shop |
| `conversationId` | String / text | Required | Unique FK to existing whatsapp.Conversation; one grant for its entire lifetime |
| `initialInboundVersion` | Int / integer | Required | Greater than zero; turn at first CommerceAgent admission, not grant identity |
| `releaseId` | String / text | Required | FK to CommerceRelease |
| `selectedCapabilityKeys` | Json / jsonb | Required | Array of 1–32 distinct capability keys from the release |
| `grantedTools` | Json / jsonb | Required | Immutable array of 0–32 exact {toolId, toolRevisionId, toolName, definitionVersion, capabilityKeys} entries, at most 65,536 bytes |
| `runnerVersion` | String / varchar(64) | Required | Non-blank exact runner version |
| `createdAt` | DateTime / timestamptz(3) | now | First admitted resolution |
| `expiresAt` | DateTime / timestamptz(3) | Optional, NULL | Future retention eligibility; not a turn execution deadline |

Unique `(conversationId)`; indexes `(shopId, createdAt, id)`,
`(releaseId)`, `(expiresAt)`. Shop and Conversation FKs use ON DELETE CASCADE /
ON UPDATE RESTRICT, so existing tenant/conversation deletion removes these
records. Release FK uses RESTRICT on delete/update. CHECK expiresAt is NULL or
later than createdAt; selectedCapabilityKeys JSON outer type/byte bound is array / 8,192 bytes; grantedTools has its separate 65,536-byte bound. V1
inserts expiresAt=NULL and implements no timer-based deletion job. Do not invent
a retention duration or expire a pin while the conversation or any retry may still use it.

Database insert trigger validates:

1. The conversation must have a non-NULL checkoutRecoveryId referencing an
   existing commerce.CheckoutRecovery. Resolve the authoritative shop exclusively
   through that recovery's shopId and require it to equal the snapshot shopId.
   Reject missing/sentinel recovery IDs and conversations without a recovery;
   Conversation.shopId is never a fallback owner. If that legacy nullable field
   happens to be populated, it must agree with the recovery owner.
2. The supplied initialInboundVersion is positive and no greater than the stored
   Conversation.inboundVersion. It records when the conversation grant was first
   established; subsequent inbound versions MUST reuse this same row. Current
   processing/staleness checks remain Background's responsibility.
3. The release has nonempty membership; selected keys are distinct JSON strings,
   include conversation_core, and each resolves to a member of that exact release.
   Current feature eligibility remains a service check, not a JSON trust claim.
4. grantedTools is an array, max32 items, <=65536 bytes, each with exactly
   toolId/toolRevisionId/toolName/definitionVersion/capabilityKeys. First three
   strings<=128; definitionVersion<=64; capabilityKeys is a sorted nonempty array
   of unique strings<=128, max32. Unique toolId and toolName. Resolve each entry
   through the named published CommerceToolRevision, its tool name/version and
   the pinned release's capability toolBindings. Each provenance capability must
   be selected and bind that exact revision. Require the entry set and provenance
   to equal the complete deduplicated union of selected toolBindings (no omission
   or invented authority); conflicting versions reject. Empty tools are valid
   for prompt-only configurations and do not grant any remote calls. Current
   eligibility and emergency enabled state are checked before insertion by the
   service, while fresh permissions are checked on each call. finalResponse is
   local host output and is never an entry in grantedTools.

Grants are immutable: reject UPDATE of CommerceConversationGrant in v1. The
first admitted agent turn creates exactly one grant; all later turns and retries
read it. Concurrent initialisation losers read the winning row after a unique-key
conflict and cannot overwrite its release, selected capabilities or grantedTools. Allow DELETE for authorised conversation/shop retention workflows;
there is no public grant-deletion/reset endpoint. Do not delete/recreate a grant
while its conversation exists to acquire more tools; deletion is only part of
the existing parent shop/conversation retention/deletion workflow. Protect the invariant on existing
Conversation.checkoutRecoveryId/legacy shopId changes and
CheckoutRecovery.shopId changes: reject an update that would detach a retained
snapshot from its recovery, attach it to another recovery, or make its shop
ownership inconsistent. Once a conversation has a retained snapshot, its recovery
link is immutable. Implement only these bounded ownership guards, not a general lifecycle
redesign. Do not change or backfill existing conversation ownership columns.

and identity. Draft allocation locks CommerceTool. Draft version changes must

### Enforcement and publishing contract

| Rule | DATABASE-001 responsibility | Consumer responsibility |
|---|---|---|
| Types, nullability, uniqueness, FKs, scalar bounds, JSON outer type/size | Prisma definitions and SQL CHECKs/triggers where Prisma cannot express them | Parse canonical shared schemas before writing |
| Published revision, pin and audit immutability | Migration triggers, tested by direct SQL attempts | Do not expose forbidden mutations |
| Release membership references published matching revision | Composite FK + publication-state trigger | Assemble exactly 1–32 members, including base, in one transaction |
| Release membership cannot change after creation | UPDATE/DELETE triggers | No insertion into an existing release; no v1 deletion API; all initial members inserted with new release |
| Concurrent draft/pointer writes | Non-negative/check-increment guards and uniqueness | CAS predicates; zero updated rows means conflict, never last-write-wins |
| Prompt/config/tool/runner validity and content hash | Structural bounds only | SHARED-001 validators; COMMERCE-003 validates bound published tool revisions, executor/schema versions and SemVer compatibility |
| Actor permission and audit of each operation | Existing-admin FKs and audit structure | NextAuth/current role checks; publish/pointer/audit write in one transaction |
| Correct tenant, selected release keys and durable conversation grant | Insert and owner-change guards plus unique conversation key | Background admission, current lifecycle/feature permission and revocation checks |

Hash contract for publication: lower-case SHA-256 of UTF-8 canonical JSON of
`{contractVersion, promptTemplate, configuration, toolBindings}`. Canonical JSON sorts object keys recursively, preserves array
order, uses JSON number/string encoding with no whitespace, and rejects non-finite
numbers. Sort toolBindings by toolId before hashing/storing. SHARED-001 owns
the reusable validator/hash-input contract; COMMERCE-003 computes the hash. No
hashing extension or provider library is required in the migration.

Add inverse Prisma relations on existing Feature, PlatformAdmin, Shop and
Conversation only as required by these FKs. Preserve their existing scalar
columns, accounts, roles, preferences and deletion policies. Do not add NextAuth
User/Account/Session tables or replace the existing Shopify Session table.
