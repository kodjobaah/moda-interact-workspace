# Connect the WooCommerce plugin to the hosted Moda API

## Architecture

Architecture ID:

`ARCH-026`

Architecture document:

`docs/architecture/ARCH-026-woocommerce-application-foundation.md`

Coordinator:

`moda_architect`

## Objective

Implement the WordPress/PHP side of the WooCommerce installation connection and authentication contract owned by `ARCH-026-API-002`.

The completed task must allow a privileged WooCommerce administrator to initiate a connection from the installed Moda plugin without exposing Moda credentials to browser JavaScript, allow the hosted Moda API to prove live control of that exact WordPress site through the API-002 HMAC challenge callback, persist the returned long-lived installation credential only in server-side WordPress state, and use it for authenticated server-to-server calls to the hosted Moda API.

The bounded runtime is:

```text
React / Woo Admin browser
        |
        | WordPress cookie + REST nonce
        v
local Moda WordPress REST route
        |
        v
PHP connection coordinator
        |
        +-- derive canonical site URL server-side
        +-- generate attemptId + ephemeral bootstrapSecret
        +-- persist short-lived bootstrap attempt server-side
        |
        | POST API-002 connect contract
        v
hosted moda-interact-api
        |
        | GET public challenge callback
        v
WordPress/PHP challenge endpoint
        |
        +-- load one active bootstrap attempt
        +-- HMAC exact API-002 proof message
        +-- return proof once
        |
        v
hosted API verifies site control
        |
        v
returns installationId + shopId + raw credential once
        |
        v
PHP persists one server-side connection record
        |
        | subsequent PHP requests
        | X-Moda-Installation-Id + Bearer credential
        v
GET /v1/woocommerce/installation
```

This task establishes the PHP-side connection/authentication boundary only. It MUST NOT implement merchant onboarding, billing, recovery, Merchant Knowledge, product/coupon access, commerce-event publication, Background integration or the final React merchant screens.

## Context

`ARCH-026-WOOCOMMERCE-001` establishes the installable PHP + React WordPress/WooCommerce extension foundation.

`ARCH-026-WOOCOMMERCE-002` establishes the supported WordPress/WooCommerce/PHP runtime, dependency gates and safe plugin lifecycle.

`ARCH-026-API-002` owns the authoritative external contract in:

```text
openapi/woocommerce-installation-v1.yaml
```

including:

```text
POST /v1/woocommerce/installations/connect
GET  /v1/woocommerce/installation
```

and the required public site-control callback:

```text
GET <canonicalSiteUrl>/wp-json/moda-interact/v1/connection/challenge
    ?attempt_id=<UUID>
    &nonce=<base64url(32 bytes)>
```

The proof message is exactly:

```text
moda-interact-connect-v1\n<attemptId>\n<nonce>\n<canonicalSiteUrl>
```

with HMAC-SHA256 keyed by the decoded 32-byte bootstrap secret generated by this plugin task.

API-002 returns the long-lived raw installation credential once and stores only its SHA-256 digest in Moda PostgreSQL. The PHP plugin therefore owns the only durable merchant-side copy required for future authenticated API requests.

The plugin executes on merchant-controlled infrastructure. Its long-lived Moda credential MUST remain server-side. Browser JavaScript must never receive the raw credential, Authorization header or bootstrap secret.

WooCommerce's REST API requires a non-Plain permalink structure. WOO-003 therefore treats working `/wp-json/` routing as a connection prerequisite rather than silently inventing an alternative callback contract. Production connection uses a public HTTPS site; ARCH-026 also permits one explicit local-development mode so the same PHP/HMAC/credential flow can be exercised against a local WordPress/WooCommerce site.

Connection/reconnection is not merchant onboarding. A successful connection MUST NOT mark onboarding complete, choose a plan, activate billing or create a Woo-specific duplicate of the existing Moda merchant/account lifecycle.

### API contract consumption

The authoritative remote contract remains API-002's OpenAPI 3.1 document.

Do not create a second independently-owned OpenAPI/schema definition in the plugin repository.

The PHP implementation and its tests may use bounded fixtures representing API-002 requests/responses, but the task must reference the API-002 contract as the source of truth rather than inventing structurally similar semantics.

### Server-side Moda API configuration

Create one server-side configuration boundary for the Moda API base URL.

During ARCH-026 pre-deployment/testing, an explicit server-side configuration such as:

```text
MODA_INTERACT_API_BASE_URL
```

may supply the API origin.

Requirements:

- configuration is read only on the PHP/server side;
- the browser cannot choose or override the remote API origin;
- default/production mode requires HTTPS;
- support one explicit server-side `public|local-development` connection mode consistent with API-002;
- `local-development` may use a local API origin such as `http://127.0.0.1:<port>` or `http://localhost:<port>` and MUST NOT accept arbitrary public HTTP API origins;
- local-development mode is never inferred from the API URL, WordPress hostname or browser input;
- the plugin must not enable local-development mode by default in the distributable package;
- no API secret is embedded in JavaScript/localized script data;
- tests may inject controlled API fixtures through repository-local dependency injection without weakening production HTTPS validation.

The final production public origin/deployment wiring remains Gateway/release work.

### Canonical local site identity

The plugin MUST derive the site identity server-side from WordPress configuration; the browser MUST NOT submit `siteUrl`.

Use the WordPress home URL as the source and canonicalize it to the exact API-002 mode-specific site rules.

Default/production mode remains:

```text
https only
DNS hostname only
no credentials
no non-443 explicit port
no query
no fragment
root without trailing slash
non-root path without trailing slash
<= 512 UTF-8 bytes
```

Explicit `local-development` mode additionally permits local WordPress identities such as:

```text
http://woocommerce-sandbox.local
http://localhost:<port>
http://127.0.0.1:<port>
```

Local-development mode does not permit arbitrary public HTTP sites and does not weaken the HMAC challenge contract.

Before initiating remote connection, require:

```text
get_option('permalink_structure') != ''
```

and verify that WordPress's generated REST URL for the challenge route resolves to the API-002 canonical callback shape under that site URL.

If the site violates the selected API-002 mode, uses Plain permalinks, produces an incompatible REST callback URL or otherwise cannot satisfy the challenge contract, fail locally before sending the bootstrap secret to Moda. In default/production mode HTTP is rejected; in explicit local-development mode HTTP is permitted only for an approved local identity.

Do not automatically change the merchant's permalink configuration.

### Local privileged connection routes

Expose local WordPress REST endpoints:

```text
GET  /wp-json/moda-interact/v1/connection
POST /wp-json/moda-interact/v1/connection
```

Both routes require:

```text
current_user_can('manage_woocommerce')
```

and normal authenticated WordPress REST cookie/nonce protection.

The browser-facing routes MUST never return:

- bootstrap secret;
- long-lived installation credential;
- Authorization header;
- credential digest;
- challenge HMAC key material;
- complete remote response bodies.

The local POST request needs no merchant-supplied site/tenant/API identity. Reject unexpected body fields rather than trusting browser-provided connection identity.

### Connection initiation

For each privileged POST connection request:

1. derive and validate the canonical site URL server-side;
2. verify the Woo/WordPress runtime and non-Plain permalink prerequisites;
3. verify server-side Moda API configuration;
4. generate a UUID v4 `attemptId`;
5. generate exactly 32 cryptographically random bootstrap-secret bytes and base64url encode them;
6. persist a short-lived server-side bootstrap attempt keyed by `attemptId`;
7. call API-002 `POST /v1/woocommerce/installations/connect` with exactly:

```json
{
  "siteUrl": "<derived canonical site URL>",
  "attemptId": "<UUID>",
  "bootstrapSecret": "<base64url 32 bytes>"
}
```

8. validate the remote response against the bounded API-002 result shape;
9. persist the returned connection state server-side;
10. always remove any remaining bootstrap-attempt state in a finally/cleanup path.

The bootstrap secret is not the long-lived credential and must never survive beyond the bounded connection attempt TTL/cleanup lifecycle.

### Bootstrap-attempt storage

Use short-lived WordPress server-side state that is visible to the concurrent challenge callback request, for example a transient keyed by a one-way/escaped representation of `attemptId`.

The stored logical data is limited to:

```text
attemptId
bootstrapSecret
canonicalSiteUrl
expiresAt / transient TTL
```

Requirements:

- TTL <= 120 seconds;
- not autoloaded as ordinary application configuration;
- never exposed to browser JavaScript;
- removed after challenge use where practical;
- removed after the outbound connect attempt completes/fails;
- an unknown/expired attempt cannot generate a proof.

The challenge endpoint should behave as a one-attempt proof boundary: once it has accepted an active attempt and computed the bounded proof, consume/delete that attempt before emitting the successful response. A failed/expired attempt must require a new connection attempt rather than extending the secret lifetime.

### Public challenge callback

Expose exactly:

```text
GET /wp-json/moda-interact/v1/connection/challenge
```

This route is intentionally reachable without a logged-in WordPress user because the hosted Moda API calls it server-to-server.

It MUST NOT be a general unauthenticated Moda API.

The route accepts only:

```text
attempt_id = UUID
nonce      = base64url encoding of exactly 32 bytes
```

For an active attempt, compute:

```text
HMAC-SHA256(
  key = decoded bootstrapSecret,
  message = "moda-interact-connect-v1\n<attemptId>\n<nonce>\n<canonicalSiteUrl>"
)
```

and return exactly the API-002 logical response:

```json
{
  "attemptId": "<same UUID>",
  "nonce": "<same nonce>",
  "proof": "<base64url HMAC-SHA256>"
}
```

Do not return the bootstrap secret itself.

Unknown, malformed, expired or already-consumed attempts return a bounded generic failure and no HMAC proof.

### Long-lived installation connection storage

After a successful API-002 response, persist one server-side WordPress option record containing the connection required for subsequent PHP API calls.

Use one canonical non-autoloaded option so metadata and its matching credential are updated as one WordPress option row rather than independently drifting.

Logical stored shape:

```text
schemaVersion = 1
installationId
shopId
canonicalSiteUrl
credential             raw base64url long-lived installation credential
credentialVersion
connectedAt
```

The exact option name is repository-local, but it must be Moda-prefixed and private to the plugin.

Requirements:

- explicit non-autoload storage;
- strict schema validation on read;
- no serialization into browser bootstrap/localized data;
- no logging of the complete option;
- no exposure through local REST responses;
- `shopId` is informational local metadata only and is never sent as authoritative tenant identity on authenticated requests;
- deactivation does not delete the connection record;
- uninstall/data-erasure policy remains out of scope.

Do not invent a custom encryption scheme whose key is stored alongside the ciphertext on the same merchant server. The security boundary for this task is server-side WordPress storage plus strict non-exposure to browser/logs; later platform hardening may add stronger host-specific secret-storage integration if justified.

### Local persistence failure after remote success

If API-002 successfully creates/reconnects the remote installation but the plugin cannot persist the returned local connection record:

- do not return the raw credential to the browser;
- return a bounded `LOCAL_PERSISTENCE_FAILED` outcome;
- preserve any previous local connection option if WordPress did not replace it;
- do not claim the plugin is connected;
- allow a later explicit connection retry to recover through API-002's reconnect/credential-rotation path.

Do not attempt to roll back the remote Shop/installation with an API that does not exist.

### Reconnect semantics

Calling the privileged local POST connection route when local connection state already exists is an explicit reconnect.

Reconnect reuses the same API-002 site-control proof and receives the provider-confirmed same installation/shop IDs with a newly rotated credential/version.

Only replace the local connection option after a complete successful API-002 response has been strictly validated.

Reconnect MUST NOT:

- create/reset local onboarding state;
- mark onboarding complete;
- alter billing/plan state;
- delete merchant configuration;
- create a second local Shop identity;
- rely on the previous credential to prove site ownership.

### Site URL mismatch / clone guard

Before using a stored long-lived connection credential, derive the current canonical WordPress site URL again.

If it differs from stored `canonicalSiteUrl`:

```text
status = SITE_URL_CHANGED
```

and do not use the stored credential for remote authenticated calls.

Do not silently reconnect the stored installation to a new domain; API-002 explicitly makes site-URL changes out of scope.

This guard prevents normal plugin execution on a cloned/migrated WordPress database from silently acting as the original site. It is not a substitute for server security if a credential is deliberately extracted from the merchant database.

### Authenticated remote client

Implement a bounded PHP `ModaApiClient` (or equivalent) using the WordPress HTTP API.

For authenticated API-002 requests send only:

```text
X-Moda-Installation-Id: <stored installationId>
Authorization: Bearer <stored raw credential>
```

Do not send local `shopId` as tenant authority.

Remote client requirements:

- HTTPS only in default/production configuration; explicit local-development mode may use an approved loopback/local API origin over HTTP;
- TLS certificate verification enabled;
- bounded total timeout;
- redirect following disabled so Authorization cannot be forwarded to another origin;
- bounded response size;
- strict JSON/media-type/result parsing;
- no cookies;
- no credential/body logging;
- map remote/network failures to bounded plugin outcomes rather than relaying arbitrary remote body text to React.

### Local connection status

The privileged local GET connection route returns one bounded browser-safe state.

At minimum support:

```text
DISCONNECTED
CONNECTED
RECONNECT_REQUIRED
SITE_URL_CHANGED
REMOTE_UNAVAILABLE
API_NOT_CONFIGURED
LOCAL_STATE_INVALID
```

When a valid local connection exists and the site URL still matches, use API-002:

```text
GET /v1/woocommerce/installation
```

to verify the currently stored installation credential.

On success return only safe metadata such as:

```json
{
  "status": "CONNECTED",
  "installationId": "...",
  "shopId": "...",
  "canonicalSiteUrl": "...",
  "credentialVersion": 1
}
```

The browser must never receive the raw credential.

A remote authentication failure maps to `RECONNECT_REQUIRED` without automatically deleting the stored local record. A network/provider outage maps to `REMOTE_UNAVAILABLE`, not `DISCONNECTED`.

## Requirements

### R1 — Browser never receives remote credential material

Bootstrap secrets, installation credentials and Authorization headers remain PHP/server-side for their entire lifecycle.

### R2 — Site identity is server-derived

The local connection route derives the WordPress site URL itself. Browser-supplied `siteUrl`, `shopId`, installation ID or API origin cannot choose the remote Moda tenant.

### R3 — Connection requires a mode-compatible REST route

Plain permalinks and incompatible/unreachable REST callback shape are rejected locally before starting remote connection. Default/production mode rejects HTTP sites. Explicit local-development mode may use only an approved local HTTP/HTTPS WordPress identity and must never be inferred from browser/site input.

### R4 — Bootstrap proof is short-lived and one-attempt

The bootstrap secret has at most a 120-second server-side lifetime and is consumed/cleaned through the bounded challenge/connect lifecycle.

### R5 — Challenge callback implements API-002 exactly

The public callback uses the exact message format, HMAC-SHA256 algorithm, nonce/attempt validation and response shape defined by API-002.

### R6 — Long-lived credential is server-side non-autoloaded state

The returned installation credential is stored only in the canonical non-autoloaded WordPress connection option and is never included in browser-visible state or logs.

### R7 — Authenticated requests resolve tenant remotely

PHP sends installation ID + credential only. It does not assert `shopId` as authorization input.

### R8 — Reconnect rotates without resetting account lifecycle

A reconnect replaces the local credential only after API-002 confirms the reconnect and must not modify onboarding, billing, entitlement or merchant settings.

### R9 — Local state and remote availability are distinct

Remote outage is not interpreted as disconnection, and remote credential rejection does not silently delete the local connection record.

### R10 — Site clone/migration does not silently reuse the connection

Current canonical site URL must match the stored connected URL before the plugin uses the long-lived credential.

### R11 — WordPress authorization protects browser-facing commands

Local GET/POST connection routes require `manage_woocommerce` and normal WordPress REST nonce/cookie authentication.

### R12 — Remote response bodies/secrets are not diagnostic output

Errors/logs expose bounded codes/identifiers only and never complete connection responses or sensitive headers.

### R13 — Local development is explicit and production-safe

The PHP plugin may use local HTTP site/API origins only through an explicit server-side local-development mode. The mode is disabled by default, is never browser-controlled, and the production package retains strict HTTPS/public behavior when no developer override is present.

## Implementation Notes

Use WordPress/WooCommerce public APIs and the WordPress HTTP API rather than introducing a second PHP networking framework without a concrete requirement.

Use `random_bytes(32)` (or an equivalently strong PHP CSPRNG) for bootstrap secrets and WordPress/PHP-supported UUID generation for connection attempt IDs.

The bootstrap transient exists only so the independent inbound challenge request can access the proof key while the original privileged connection request is blocked waiting on the hosted API. Do not replace it with browser state.

Do not use the WordPress site/domain itself as steady-state authentication. After connection, installation ID + credential are the only external credentials and Moda resolves the authoritative Shop server-side.

Do not automatically reconnect on page load. Credential rotation is an explicit merchant/admin action because it invalidates the previous credential.

Do not treat a transient remote outage as evidence that the merchant disconnected or lost their Moda account.

WooCommerce documents that its REST API requires non-Plain WordPress permalinks. WOO-003 therefore checks this prerequisite instead of changing store permalink configuration as a side effect.

Connection and reconnect derive site identity from WordPress, require non-Plain permalinks and compatible REST URL shape, and use UUID-v4 attempts with a 32-byte CSPRNG bootstrap secret. The public callback consumes one active attempt and returns only the exact HMAC proof. The bounded WordPress HTTP client enforces TLS verification, five-second timeout, no redirects/cookies, an 8 KiB response bound, strict JSON/result shape, and canonical installation authentication headers.

The privileged REST façade requires `manage_woocommerce` and standard REST cookie/nonce authentication, rejects all request identity input, and returns only safe statuses/metadata. Local credentials are stored in one strict non-autoloaded option; site changes block credential use; remote 401/outage and local persistence failure remain distinct; retries can recover without altering unrelated onboarding state. Deactivation/reactivation preserves the connection. No WOO-004 UI or merchant business capability was added.
