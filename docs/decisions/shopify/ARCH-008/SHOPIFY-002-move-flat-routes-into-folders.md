# ARCH-008-SHOPIFY-002: Move Shopify app routing from flat files into route folders

## Architecture

Canonical: `docs/architecture/ARCH-008-shopify-app-pricing-conformance.md`

## Objective

Replace the Shopify app's flat route-file layout with folder-based route modules
that make route ownership and nesting explicit, while preserving the existing
React Router filesystem routing behavior and every public URL used by the
embedded merchant application.

## Context

The app currently uses `@react-router/fs-routes` through `app/routes.js` and
keeps route modules in a flat naming scheme such as:

- `app/routes/app.jsx`
- `app/routes/app.billing.tsx`
- `app/routes/app.billing.callback.tsx`
- `app/routes/app.billing.select.jsx`
- `app/routes/app.merchant-support.jsx`
- `app/routes/app.pending-recoveries.jsx`
- `app/routes/app.usage.jsx`
- `app/routes/webhooks.app.uninstalled.jsx`

This layout obscures parent/child relationships and makes route-local assets and
future nested pages harder to maintain. The migration must be structural, not a
URL redesign.

## Required preflight

1. Work only in the launcher-resolved `ARCH-008-SHOPIFY-002` implementation
   worktree.
2. Confirm the repository still uses React Router filesystem routing and identify
   the installed `@react-router/fs-routes` folder convention for layout/index,
   dynamic, resource, and splat routes.
3. Inventory all current route modules, generated route types, imports, links,
   tests, and build artifacts that refer to flat route paths.
4. Confirm the current URL and parent-layout contract for application routes,
   billing routes, webhook/resource routes, health/readiness routes, and privacy.
5. If the installed router cannot represent the required folder layout without a
   URL change or unsupported compatibility convention, stop and report the exact
   constraint before editing.

## Scope

- Move the relevant `app/routes` modules into the folder layout supported by the
  installed React Router filesystem-route package.
- Preserve route URLs, HTTP methods, loaders, actions, redirects, headers,
  authentication boundaries, error boundaries, and parent `<Outlet>` behavior.
- Keep route-local styles and assets colocated where that improves ownership,
  without changing unrelated application styling.
- Update focused tests and imports to the new source paths.
- Update route documentation or source comments only where they describe the old
  flat layout.
- Let generated `.react-router` types/build output be regenerated by the normal
  toolchain; do not hand-edit generated artifacts.

## Required implementation

### A. Folder topology

Use explicit folders for nested application routes. At minimum, the resulting
layout must make the following relationship visible in source:

```text
app/routes/app/
  route module for `/app`
  billing/
    route module for `/app/billing`
    callback route module for `/app/billing/callback`
    select route module for `/app/billing/select`
```

Apply the same folder convention to other nested app areas where the router
supports it, including merchant support, pending recoveries, usage, and webhook
families. Do not create duplicate route modules as a compatibility shortcut.

### B. URL and behavior preservation

The migration must preserve at least:

- `/app`
- `/app/billing`
- `/app/billing/callback`
- `/app/billing/select`
- `/app/merchant-support`
- `/app/pending-recoveries`
- `/app/usage`
- existing webhook, `/health`, `/ready`, and privacy routes

Preserve route IDs where the filesystem convention allows it, and document any
router-required route-ID change with evidence that URL behavior is unchanged.

### C. Verification

Add or update focused route tests that verify the route manifest and the behavior
of the moved billing and application routes. Test source imports must target the
new canonical modules rather than relying on compatibility re-export files.

Run route generation/type generation as part of validation and ensure no stale
flat route module remains under `app/routes` for a moved route.
