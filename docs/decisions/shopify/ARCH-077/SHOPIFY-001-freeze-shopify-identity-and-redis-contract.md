# Freeze Shopify consent identity and Redis contract

## Architecture

[ARCH-077](../../../architecture/ARCH-077-shopify-owned-whatsapp-checkout-consent.md). **S001 definition and cart-to-checkout correlation proof accepted by architect (17 November 2026); `complete` refers to contract/evidence, not application implementation.** SHARED-001 may start now; downstream tasks still execute their stated acceptance tests before activation. No runtime changes are included here.

## Objective

Freeze the Shopify cart, checkout and authenticated customer identities and exact Redis contract before any Shopify or Background writer/reader is built. This is a proof gate, not an invitation to infer a correlation mechanism.

## Existing touchpoints for inspection (do not change runtime in this definition)

- `shopify.app.moda-interact.toml` (current cart/checkout webhook subscriptions and Shopify API version).
- `app/services/webhooks/checkout-normalization.ts` (`checkoutToken` and `cartToken`).
- `app/services/webhooks/cart-activity-normalization.ts` (cart `token`, `isEmpty`).
- `app/services/webhooks/shopify-webhook-ingress.service.ts` and `app/services/webhooks/shopify-webhook-queue.server.ts` (authenticated producer and BullMQ publication).
- Background's `src/domain/pending-recovery-candidate.ts` and `src/services/pending-recovery-candidate/candidate-index.store.ts` (existing Redis index ownership).

## Requirements

### 1. Consent scope and decisions — frozen business rules

- [ ] **Merchant-scoped customer permission:** An explicit opt-in is the customer's permission to receive the merchant's WhatsApp shopping updates, reminders and offers. It is **not limited to the cart or checkout on which the customer selected the checkbox**. For a reliably identified Shopify customer, the permission can authorise later eligible checkouts at the same merchant without another selection. Do not extend permission across merchants.
- [ ] **Cart/checkout correlation, not permission ownership:** The cart and checkout tokens connect the initial selection to the correct recoverable checkout. They are not the permanent customer identity and must not become competing independent permission authorities.
- [ ] **Explicit action precedence:** Within one verified cart/checkout, the latest *acknowledged deliberate* action determines its **temporary** choice. Across two distinct eligible recoveries, only their successfully materialised decisions change current PostgreSQL permission; after Cart A has materialised GRANT and Cart B has later materialised REVOKE, B governs new proactive outreach. Prior A retry/duplicate is never a new regrant. Ordinary cart/checkout webhooks, page loads and unchecked defaults are **not** consent actions; temporary B REVOKE has no cross-recovery effect before B is recoverable.
- [ ] **Deferred recovery materialisation:** Store only the acknowledged explicit selection against the *current cart/checkout* in temporary Redis; do not create a permanent customer-level Redis preference or consent history. For a verified returning customer, S002 reads existing customer permission from PostgreSQL. Only when an abandoned checkout is independently verified as recoverable does Background apply the latest accepted GRANT/REVOKE to the existing `Customer`/`CustomerPhone` permission and associate the selected recipient. Materialisation must never manufacture a grant. Do not create consent by detecting a cart, checkout or phone number.
- [ ] **No new SQL contract:** Do not add a database model, field, enum value, migration or table; do not insert Moda-owned Shopify evidence into Woo-only `WhatsAppConsentEvidence`. For ARCH-077 the **existing `SHOPIFY_NATIVE` enum value designates Moda-verified Shopify checkbox evidence** after eligible recovery materialisation; it must not trigger or imply a Shopify-native marketing-consent API read. The current durable customer permission resides in existing PostgreSQL records, and the active checkout selection remains temporary Redis state. Preserve all SQL constraints, revisions and STOP.

### 2. Shopify cart and checkout correlation — verified event identities

- [ ] **Observed correlation:** Real tests from 17 November 2026 prove that stripping the private query portion from `/cart.js` token matches `carts/create/update` webhook `token` in two trials; `checkout.cart_token` differed in two trials and matched in a third. A diagnostic cart attribute propagated into `checkouts/create/update` `note_attributes` in the third trial. Therefore **do not require raw cart-token equality between cart and checkout** and do not infer identity from email, phone, products or timing. The experimental marker does not prove secure consent ownership.
- [ ] **Cart-page action:** Bind a deliberate action to the authenticated shop, approved storefront cart-action proof and current Ajax cart. S002 issues one server-created marker per current verified shop/cart; S003 writes it to the real Shopify cart. The marker must be read back before presenting/accepting the Moda checkbox and cannot be treated as a grant on its own.
- [ ] **Checkout transition:** B001 consumes a marker found under the exact `note_attributes` key in an authenticated `CHECKOUTS_CREATE` **or** `CHECKOUTS_UPDATE` event, resolves it via S002's server-issued Redis mapping and binds the checkout-token identity. Cart-webhook attribute fields are not required. If CHECKOUTS_UPDATE arrives before CHECKOUTS_CREATE, the result must still be idempotent and correct.
- [ ] **Conflict:** An absent, malformed, unknown, expired, cross-shop, forged or conflicting marker is not a grant and cannot be repaired by matching contact information, basket contents or timestamps. Distinct checkout tokens claiming one marker are ambiguous until independently and deterministically resolved under accepted Shopify identity evidence; never silently attach one consent selection to multiple unrelated checkouts.
- [ ] **Shopify Plus:** Verify the supported Checkout UI Extension target, signed session token and checkout-token availability, then associate a selection directly with the checkout identity. No intermediate cart alias is needed. Record unsupported/accelerated checkout paths explicitly.

### 2A. Frozen v1 marker and Redis cross-repository contract (architect amendment)

The exact **cart correlation marker** contract for S002/S003/B001 is fixed below. Guest action uses the fixed **low-trust temporary choice + verified Shopify checkout binding** protocol in item 11; there is no new browser-session authentication system to design. The execution agents must prove this scheme under their acceptance tests, not design another scheme before they can begin.

1. **Attribute:** Shopify cart attribute key `moda_cart_correlation_v1` (not the temporary `moda_s001_probe`). Use one exact key across S002, S003 and B001. It carries only an opaque marker, never a decision, phone, customer ID or shop secret. The attribute is shopper-visible/mutable and therefore provides **correlation evidence, not authorisation or proof of consent**. Do not write to checkout notes or orders to establish permission.
2. **Issuance:** On S003 cart-block initialisation, after the Shopify app has verified the signed App Proxy shop context and current cart/session ownership under S001, S002 creates `const marker = "m1_" + randomBytes(32).toString("base64url")` using Node `node:crypto`. The value has 256 random bits and 46 ASCII characters. Never use `Math.random`, client `crypto.randomUUID`, timestamps, cart contents, phone/email or a deterministic shop identifier as the production marker. One currently active shop/cart gets **one** marker; parallel preparers return the same persisted winner, not competing markers. Marker issuance is neutral; it is not a GRANT.
3. **Canonical identities:** `shopId` is the immutable authenticated Moda shop ID; clients cannot choose it. `cartBaseToken = ajaxCartToken.split("?")[0]` (case-preserving; opaque nonempty string; no URL-decoding, lowercasing or trimming); ignore the private query component and never persist/log it. Checkout `token` is a separate, opaque, nonempty checkout identifier. Reject cart-base and checkout tokens outside **1–512 UTF-8 bytes** before hashing, and validate marker format exactly against `^m1_[A-Za-z0-9_-]{43}$` plus decode/re-encode to exactly 32 bytes; preserve case and reject ambiguity. S001 must verify these limits against current Shopify values. Store no raw cart/checkout token in Redis or logs.
4. **Temporary Redis key encoding — no new cryptographic secret:** Cart and checkout identifiers are opaque; to avoid placing their raw values in Redis keys compute `digest(kind,value) = SHA256(UTF8("arch077:v1\0" + kind + "\0" + shopId + "\0" + value)).hex` using built-in `node:crypto`, with `kind` exactly `cart` or `checkout`. Preserve all input bytes and use the full 64 lowercase hex characters. **Do not introduce `SHOPIFY_CONSENT_HMAC_KEY_V1`, custom encryption, a new HMAC signing scheme or any cryptographic service.** The marker is already a 256-bit random public cart attribute, not an authentication secret; index it directly under the authenticated shop and validate its fixed shape. The Shopify app and Background share only the versioned format and existing Redis connection, not another secret.
5. **Exactly three short-lived record families:** `shopify:consent:v1:cart:<shopId>:<cartDigest>` holds `{v:1,shopId,cartDigest,marker,issuedAtMs,expiresAtMs,latestExplicitChoice?,choiceRevision?}`; `shopify:consent:v1:marker:<shopId>:<marker>` holds `{v:1,shopId,cartDigest,issuedAtMs,expiresAtMs,checkoutDigest?}`; `shopify:consent:v1:cart-link:<shopId>:<checkoutDigest>` holds `{v:1,shopId,cartDigest,marker,checkoutDigest,linkedAtMs,expiresAtMs}`. Read/update these **only using authenticated `shopId`**, and delete them through normal bounded cart/checkout terminal or materialisation cleanup. Plus checkout uses its existing separate checkout-keyed selection. Cart choice records also retain S001's agreed action/disclosure evidence; marker/association records never contain the consent decision and are not permanent customer history.
6. **Atomic prepare:** S002 uses one bounded Redis Lua script or WATCH/MULTI transaction to `SET` the cart and reverse-marker records together with TTL, if absent; if present it validates and returns the existing stored marker without refreshing/replacing an unrelated cart ownership or accepted choice. Reject a mismatched version/owner or partial/conflicting record. Do not create a separate queue or permanent customer-preference mirror. The marker may be returned to the owning storefront and kept in Redis **values** for idempotent read-back; it is not an authentication secret and must not be logged. On repeated prepare for a verified shop/cart, never rotate the marker while an accepted choice or bound checkout still exists.
7. **Theme write/read-back:** S003 POSTs `{attributes:{moda_cart_correlation_v1: marker}}` to the locale-aware storefront `cart/update.js`; confirm the returned cart contains that same attribute and, if needed, re-fetch `/cart.js`. Only then enable the Moda checkbox and allow an explicit consent action. A failed marker preparation/write/read-back hides only Moda's control and never blocks checkout. A changed cart token requires a newly prepared marker and a successful replacement write before further choices; do not reuse the old cart's decision silently.
8. **Verified webhook binding:** B001 parses `note_attributes` (Shopify's array `{name,value}` or mapped object) on authenticated `CHECKOUTS_CREATE` and `CHECKOUTS_UPDATE`. It accepts exactly one nonempty, correctly formatted `moda_cart_correlation_v1`; zero yields **missing**, conflicting repeated values yield **ambiguous**. It looks up the validated random marker under the *authenticated* `shopId`, loads the marker/cart records, verifies versions, shop scope, reciprocal cart ownership, live TTL, and current owner, then atomically assigns the checkout digest once. A duplicate checkout is an idempotent read. Different checkout token for an already-bound marker is **ambiguous**, never an automatic reassignment. Bind only the **cart choice reference**, never write a GRANT due to a webhook.
9. **Checkout `cart_token`:** B001 reports `MATCH`, `MISMATCH` or `MISSING` against the original cart digest; webhook marker association may be recorded even when the cart tokens differ (observed twice). **B002 alone decides consent materialisation:** guest requires `MATCH`; `MISMATCH` or `MISSING` is allowed only for a verified signed-logged-in Shopify customer ID equal to the authoritative checkout customer ID under the same shop. No marker-only authorisation, phone/email matching or inferred owner is permitted.
10. **Sequencing and TTL:** The `cart` and `marker` records are created before a consent choice and may be read by either webhook delivery order; choices remain on the cart record and are not copied into checkout event/BullMQ payloads. Orphan carts use a maximum 48-hour sliding TTL after verified cart activity. Once a checkout is linked, retain all three records for `max(48h, configuredInactivityDelay + existingBoundedShopifyVerificationAndMaterialisationRetryWindow + 24h)` starting at linkage, with verified retries refreshing only within the bounded policy; if the retry bound cannot be established from actual code, stop. This is **not** `checkoutRecoveryLifetimeDays` and must not inherit BullMQ index TTL. Cleanup uses B001's confirmed terminal/success outcomes with compare-and-delete owner/revision checks. An expired/evicted marker yields no new grant.
11. **Security boundaries (frozen):** Signed App Proxy authenticates the merchant but not an anonymous shopper. For cart `prepare` and `choice`, the browser supplies the current Ajax cart token as an **untrusted locator** and the server verifies the authenticated shop, cart/marker reciprocal Redis owner and expected revision; the only result is a temporary choice. `choice` never changes SQL or sends. At B002 recoverability the *authenticated Shopify webhook* must independently establish the checkout/cart binding: for a **guest action** `checkout.cart_token` must match the recorded cart-base digest; for a **verified logged-in action** the signed App Proxy `logged_in_customer_id` recorded on acceptance must match the authoritative checkout `customer.id` in the same shop (regardless of an observed cart-token mismatch). Additionally require valid marker, one-to-one checkout binding, attributable canonical recipient and STOP/SQL fences. Any other combination denies materialisation and new outreach. An untrusted client-supplied customer ID, copied marker by itself, email/phone/basket/time match or fabricated client-side read-back is insufficient. No additional cookie/JWT/session manager, HMAC secret or persistent schema is authorised. Test cross-cart copied markers, swapped customer sessions, missing checkout cart tokens and mismatch cases; fail closed with typed outcomes rather than creating alternative auth. Plus uses its verified signed extension session/checkout binding.
12. **Checkout event transport:** The checked 13 November snapshot's Shopify checkout normalizer **does not forward `note_attributes`**, and both Shared V2 create and V3 update payload objects are `.strict()`. SHARED-001 is therefore a prerequisite for S002 and B001: add optional `cartCorrelationMarker` and `cartCorrelationMarkerStatus` to existing checkout payloads, without forwarding the whole attribute array or adding a queue. S002/ingress classifies the exact authenticated webhook `note_attributes` key into `PRESENT`, `ABSENT`, `INVALID`, `AMBIGUOUS` and forwards the marker value **only for `PRESENT`**, after shape validation; no legacy field (`undefined`) means `NOT_OBSERVED` to B001, not verified absence. Pin the compatible Shared package in Shopify and Background before deployment. B001 must not attempt to read raw `note_attributes` from current queue jobs.
13. **Diagnostic lifecycle:** Only the earlier local test used browser-generated `moda_s001_probe`; production issuance uses the server-generated marker and the new attribute key. `ARCH077_S001_DIAGNOSTICS` logging is temporary and must be disabled/removed after the verification evidence is recorded. Never retain raw correlation values in server logs.

**Cross-repository SHA-256 key fixtures:** `shopId = "shop-test-1"`, `cartBaseToken = "cart-test-abc"`, `checkoutToken = "checkout-test-xyz"`. `digest("cart", cartBaseToken)` must equal `0a94ff8d890538741764fd84a838b283a1b05f4f73cb6ea86e2d07bf3d9127c7`; `digest("checkout", checkoutToken)` must equal `7125b952f6bdaf71d8fcf620cf091989e659dfb58a9952125479110efb5039cd`. `cart-test-abc?key=private-test-only` canonicalises to `cart-test-abc`. The sample `m1_AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA` is an illustrative opaque marker kept verbatim as the marker-index component, not a consent proof. There is no HMAC key and no separate key rotation.

**Executed evidence, 17 Nov 2026:** Test 1 Ajax base/cart `849c6baf6d2ee352` vs checkout-cart `aeb0611cb90efe17`; test 2 Ajax base/cart `75a15a4839ae924c` vs checkout-cart `0a4a76f4680b66a3`; test 3 cart/checkout-cart `211c7a386b3e2581`, diagnostic marker browser + checkout-create/update `ef5dbf7582291225`. Test 3 demonstrates marker *propagation*, not server issuance, adversarial safety, guest authority, Plus support or multi-checkout semantics. Do not claim those tests have executed.

**Accepted scope:** The three real-browser tests completed the cart-to-checkout *propagation* investigation. The production guest path is **not** deemed secure by marker propagation alone; its exact additional checkout cart-digest matching rule and authenticated customer fallback are frozen in item 11. S002/B001/B002 must verify this rule with tests before activation. Implementers have no authority to replace it with a cookie, JWT, fingerprint or marker-as-consent shortcut.

**Runtime verification owned by implementation tasks:** S002 validates the signed App Proxy, Redis atomic prepare/choice and shop/customer claims; B001 validates the strict marker event/Redis one-to-one association; B002 validates guest cart-digest equality or verified-customer ID equality, recipient/STOP and SQL ordering; S004 validates Plus signed checkout context; SYSTEM-TEST-001 certifies the real-browser path, retries, replay and worker isolation. Return exact commands/SHA/config/fixtures. Failure blocks the affected feature/release, **not the start of unrelated prerequisite implementation**.

### 3. Returning customer on a new cart

- [ ] **Verified returning identity:** Obtain a shop-scoped authenticated Shopify customer ID through an appropriate verified Shopify context (e.g. signed App Proxy `logged_in_customer_id` where supplied, or verified checkout extension identity). Use `shopId + Shopify customer ID` to retrieve the existing preference even where the new cart token differs from the prior visit.
- [ ] **Status and opt-out:** A returning authenticated customer with a current verified PostgreSQL grant sees the checkbox checked on a new cart and may explicitly uncheck it. This records a temporary checkout/cart REVOKE; **it does not immediately modify PostgreSQL or earlier recoveries**. Only if the current checkout becomes recoverable does B002 materialise REVOKE. If it completes normally, temporary Redis is cleaned up and a later new cart reads the still-current SQL state. Do not silently regrant on page load.
- [ ] **Initial identity unknown:** A guest can select a checkbox tied to the current verified cart/checkout; establish customer identity later only from the authoritative checkout/customer association. A guest starting a separate new cart without verified continuity must not inherit a previous guest's permission from matching contact details. If a customer cannot be identified, preserve only the verified checkout-scoped evidence until identification or expiry.

### 4. Recipient selection at recoverable checkout

- [ ] **No phone field on cart:** Consent is collected before Shopify necessarily knows the customer's number. It is logically the customer's permission, not a checkbox grant for a hard-coded phone value. At recovery maturity, read the authoritative Shopify abandoned checkout using the existing lookup and resolve an available contact candidate in this priority: **customer phone → billing phone → shipping phone**.
- [ ] **Normalisation and association:** Normalise the chosen phone under the published Shared international phone contract and associate it with the correctly identified shop/customer/recovery using existing models when possible. An invalid first-preference number must not become an authorised recipient; document whether a lower-priority valid number can then be used. A shipping number supplied for a different person must not be treated as that person's opt-in solely because it appeared on the address; classify unsupported identity evidence and deny that recipient.
- [ ] **Multiple numbers:** Do not automatically reject a checkout merely because customer, billing and shipping phone fields differ; use the frozen priority to select the first eligible customer-associated number. No Shopify-native WhatsApp marketing-consent read, Shopify Messaging dependency, or `customer.defaultPhoneNumber.whatsAppMarketingConsent` requirement.
- [ ] **STOP:** Even a newly accepted checkbox `GRANT` must never clear an authoritative customer STOP, existing no-contact restriction or independently established outbound eligibility block.

### 5. Redis contract, isolation and retention

- [ ] Freeze the versioned Shopify-only key namespace and exact encoding for **temporary cart choice, temporary checkout choice, verified cart-to-checkout association and bounded action/revision evidence**. Do not allocate permanent Redis customer-preference or history keys. Provide cross-application digest/key test vectors without exposing raw cart, checkout or customer IDs in keys or logs. Shopify and Background must use identical versioned semantics and safe deployment ordering.
- [ ] Use the latest explicit action per verified cart/checkout with idempotent ordering; prior customer-level permission is read from PostgreSQL, not maintained as a second Redis authority. Checkout and cart association must not introduce competing grants. Define idempotent retries, monotonic accepted revisions, bounded atomic Redis updates and explicit behaviour when writes/read results arrive out of order. **Do not introduce a distributed-lock framework solely for checkbox selections.**
- [ ] Define **temporary** cart/checkout state retention through the normal configured maturity and bounded provider-verification/materialisation retries. B001 removes it after successful B002 materialisation or definitive completion/ineligibility; an active cart without a checkout has separately bounded retention. Later follow-ups and long-term customer permission use PostgreSQL and must **not** extend temporary Redis retention. Do **not** blindly inherit short-lived candidate-index TTLs. Missing, corrupt or evicted proof must not be interpreted as `GRANTED`.
- [ ] Inspect current shared `REDIS_URL`/DB/ACL, memory budget, eviction/persistence/backup policies and worker cleanup. Introduce no new global Redis setting without an explicit impact assessment. Never repurpose, overwrite, delete, extend TTLs of or scan Background-owned `pending-recovery:index:*`, `pending-recovery:lock:*`, `pending-recovery:order-completed:*` or BullMQ-managed keys.
- [ ] Document shopper-side checkout-unavailable behaviour: accepting a choice requires successful Redis acknowledgement, but cart/checkout must remain usable when Moda or Redis is unavailable; unverified states do not authorise recovery.

### 6. Background and outbound boundary — contract only

- [ ] Freeze the exact read inputs and outcomes required from Shopify's Redis consent service by `BACKGROUND-001` (cart↔checkout association) and `BACKGROUND-002` (maturity, recipient, STOP and proactive-send admission). Neither task may infer an opt-in from a webhook or copy consent data into an existing BullMQ job merely for convenience.
- [ ] Keep S001 focused: **PostgreSQL remains authoritative after materialisation**, and B002 reuses the existing current-permission preflight and short SQL final-send check for initial sends, retries and follow-ups. No Redis read in the SQL transaction and no Redis/PostgreSQL distributed dispatch lock. A temporary REVOKE has no durable effect on existing recoveries until an eligible checkout materialises it, per the approved lifecycle; do not accidentally claim click-time SQL withdrawal. STOP remains immediately authoritative under its existing independent pathway.
- [ ] Freeze the B002 handoff: the existing `SHOPIFY_NATIVE` value represents Moda Shopify checkbox consent **once materialised**, not native provider consent. B002 must replace the old Shopify marketing-consent reader/writer while keeping the existing SQL final-send fence, STOP, shop/recipient ownership, credit and billing checks intact. Do not delete the current fence or call the retired Shopify native marketing API.

### Mandatory deterministic recovery-decision protocol / proof gate

- [ ] The only effective consent mutation point is **B002 after recoverability independently passes** (authoritative abandoned checkout, order/payment guards, merchant-configured delay, customer and attributable recipient verified). The old `GRANTED` prerequisite must be moved *after* verification/materialisation, not used to suppress B's REVOKE. If B selects REVOKE but is paid/completed/not independently recoverable, write **zero** consent SQL changes and clear its Redis choice only on terminal completion.
- [ ] Keep two distinct orders: (a) latest acknowledged deliberate action within one cart/checkout is the temporary selection; (b) latest successfully and uniquely materialised **eligible checkout** updates persistent permission across carts. Cart creation, action click time alone, and worker scheduling do not themselves affect SQL. Duplicate/replayed A after B must not count as a new decision. Only an explicit subsequent eligible GRANT reauthorises after B's REVOKE; STOP remains separate.
- [x] **Architect-frozen trust boundary:** App Proxy validates shop at `prepare`/`choice`, but temporary cart input remains untrusted and cannot authorise send or SQL. The **authenticated checkout** supplies the binding at recoverability: exact guest cart-token digest match, or same verified Shopify customer ID captured from signed logged-in context at action time. B002 additionally validates attributable recipient and STOP. For a mismatch with no verified customer ID, reject materialisation. This is an implementation contract with negative tests, not a requirement for S001 to repeat browser token experiments or devise new session technology.
- [x] **Defined materialisation design:** B002 owns the existing short SQL row-lock/comparison contract, using the immutable server-accepted action time in `whatsappConsentProviderObservedAt` as set out in B002; only independently recoverable checkouts are candidates. No earlier selection changes permission. B002 must **test**, not redesign, crash/retry behaviour; if the existing schema cannot enforce the specified invariant, return `MATERIALISATION_IDEMPOTENCY_BLOCKER` before SQL-consent implementation/activation. Any new schema or different ordering policy requires a separate architect decision.
- [ ] Enumerate exact evidence for temporary marker propagation and optional Shared fields, including fixed cart/checkout SHA-256 key fixtures, `PRESENT` only with a validated marker, `INVALID`/`AMBIGUOUS` without marker and absence vs legacy omission. The only new checkout payload fields are `cartCorrelationMarker` and `cartCorrelationMarkerStatus`; add no cart token, full attributes, consent choice, email or phone. Never log the raw marker. No extra HMAC secret.
- [x] **Architect acceptance, 17 November 2026:** Marker propagation and the v1 contract definition are accepted. SHARED-001 can be claimed now, without repeating S001. Runtime checkout binding, SQL crash-safety and Shared schema round-trip are implementation acceptance tests in their own tasks; they are not falsely reported as completed by S001.
