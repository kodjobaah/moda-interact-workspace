# ARCH-010-ADMIN-004: Grant audited promotional recovery credits to an individual shop

## Objective

Add an internal SUPER_ADMIN-only workflow that grants a positive quantity of promotional recovery credits to one known shop with durable provenance, idempotency and audit history.

Merchants never access `moda-interact-admin`.

This task establishes the reusable one-shop grant primitive used by targeted campaign grants in ADMIN-005.

Also inspect the current `adjustAllowanceAction` implementation. Do not reuse its `FREE_RECOVERY_LIFETIME` semantics for promotional grants.

## 1. Permission boundary

Grant mutation requires the existing SUPER_ADMIN mutation boundary.

Read-only promotional balance/history may follow existing protected Admin read rules, but ordinary merchant authentication MUST never reach this action.

## 2. Grant form/data

The one-shop grant accepts:

```text
shopId
quantity                 positive whole integer
grantType                DATABASE-009 enum
reason                   required, non-blank
campaignReference        optional; required by ADMIN-005 campaign workflow
requestKey               opaque idempotency token generated by the protected UI
```

Validation requirements:

- reject zero/negative/non-integer/unsafe integer quantity;
- reject unknown grantType;
- trim and reject blank reason;
- bound strings using schema limits;
- do not infer shop from merchant-controlled data;
- do not accept a counter enum from the form; the action always targets `PROMOTIONAL_RECOVERY_CREDITS`.

## 3. Transactional grant algorithm

Inside one database transaction:

1. resolve the target shop by exact internal shop id;
2. create/reconcile `PromotionalCreditGrant` using `requestKey`;
3. create the shop's promotional `ShopEntitlementCounter` if absent;
4. increment `grantedQuantity` by exactly the grant quantity and increment counter version;
5. create `BillingAuditEvent(action=PROMOTIONAL_CREDITS_GRANTED)` with shop/admin/grant id and bounded before/after balance evidence.

### Idempotency

If the same `requestKey` is submitted again with the same:

```text
shopId, quantity, grantType, reason, campaignReference
```

treat it as an idempotent success and MUST NOT increment credits or write a second audit event.

If the same requestKey exists with different semantic fields, fail closed and log the mismatch; never reinterpret it.

Do not implement idempotency only in React/UI state. The database unique key is authoritative.

## 4. Shop lifecycle independence

Admin may grant promotional credits to any durable known shop, including one currently:

```text
ACTIVE
UNINSTALLED
NO_CONTRACT
FROZEN
reinstall pending
```

The grant changes only ownership of promotional capacity. It MUST NOT activate business execution or subscription state.

The Admin UI must clearly show whether the current shop is executable, but must not block a legitimate pre-provisioned beta/test grant solely because there is no current subscription.

## 5. Balance/history presentation

In the tenant billing/control view show separately:

```text
Promotional granted
Promotional committed
Promotional reserved
Promotional remaining
```

and recent grant provenance:

```text
quantity
grant type
reason
campaign reference when present
granted by
created at
```

Do not merge this with:

- legacy pre-ARCH-010 lifetime Free allowance adjustments;
- purchased top-up history;
- paid monthly allowance.

## 6. No Shopify / no direct Background coupling

The grant action MUST NOT:

- call Shopify;
- create an App Event;
- create a BillingPeriod;
- write a RecoveryCreditPurchase;
- call Background code/package directly;
- claim blocked recoveries resumed immediately.

BACKGROUND-009's repair scan provides durable eventual resume after a grant restores capacity.

## Required tests

At minimum prove:

1. non-SUPER_ADMIN cannot grant;
2. valid grant writes one provenance row;
3. valid grant creates missing promotional counter and increments granted quantity;
4. subsequent grant increments existing counter;
5. duplicate requestKey + identical payload is exactly-once;
6. duplicate requestKey + different payload is rejected;
7. invalid quantity/reason/type is rejected;
8. grant to NO_CONTRACT/FROZEN/UNINSTALLED shop is allowed but does not mutate lifecycle state;
9. action never writes FREE_RECOVERY_LIFETIME;
10. action never writes BillingAllowanceAdjustment;
11. action never creates RecoveryCreditPurchase/UsageEvent/App Event state;
12. audit event references the promotional grant;
13. tenant UI shows promotional balance separately;
14. merchant routes/auth are unaffected.

Run focused security/action tests, repository-declared typecheck/lint/build/full tests as applicable, and `git diff --check`.

## Non-goals

Do not:

- grant to multiple shops in one UI action;
- expire/revoke promotional credits;
- refund promotional credits;
- send merchant notifications;
- bypass subscription execution gates;
- modify the five lifetime Free grant;
- expose Admin to merchants.

## Stop conditions

Stop and return to `moda_architect` if:

- DATABASE-009 Prisma client is unavailable;
- existing Admin role enforcement differs materially from the inspected SUPER_ADMIN boundary;
- exactly-once mutation cannot be implemented without changing database schema;
- implementation requires Background or Shopify repository edits.
