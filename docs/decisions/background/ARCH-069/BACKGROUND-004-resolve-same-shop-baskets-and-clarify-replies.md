# Resolve shop and basket replies and resume the original question after clarification

## Architecture

[ARCH-069 — WhatsApp sender pool and checkout reply routing](../../../architecture/ARCH-069-whatsapp-sender-pool-and-checkout-reply-routing.md). R14 portable task definition. Implementation owner is `moda_background` in `moda-interact-background`. Coordination belongs to `moda_architect`.

## Objective

When a customer has several eligible checkouts at one proven shop, pass the customer's actual moderated question and the full list of saved items in every candidate basket to the shop-scoped routing model. It nominates one checkout and estimates how confident it is that the customer means that checkout. A valid nomination at **80% or above** routes the original question to that checkout's existing conversation. Lower confidence or an abstention triggers the clarification template. The customer sees the proven shop’s public name once, then the items in each eligible basket grouped under that basket’s number. Preserve the customer’s original question for their answer. See §3.1 for the named quote instruction when a complete numbered list cannot be presented. Exact customer selections and verified checkout quotes still use their direct routes. The score applies only to semantic selection among baskets of one verified merchant.

| Customer on one registered sender                                   | What the routing layer retains or passes on                                                                                                                                                                                                     |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two contacted shops; “Can it arrive Friday?”                        | Save this exact message as Q1 on the customer/sender thread. Ask which store. Each customer-facing Q-reference has the hashed format in §3.7; Q1 and Q2 here are illustrative.                                                                  |
| Before answering, customer asks “Can I collect my Shop B order?”    | Treat this as Q2. If B has one eligible basket, its existing agent gets the collection question. Q1 stays open.                                                                                                                                 |
| Customer quotes Q1's prompt and writes “Shop A”. A has two baskets. | Bind only Q1 to A. Compare its original delivery question with A's baskets. If the model abstains or its score is below 80%, name Shop A and show its complete, distinguishable item lists, one numbered option per basket, on the same number. |
| Customer replies “2. Can I collect on Friday?”                      | The selected A basket receives the original delivery question and the precise collection question. The merchant transcript keeps the complete answer. The other basket and Shop B receive no part of this exchange.                             |
| Customer replies with a plain “2” instead                           | The selected basket's agent answers the original delivery question only. The merchant can see the original and the choice as two authentic messages.                                                                                            |

**Delivery.** Every new BG004 customer-facing clarification is an in-session, free-form WhatsApp text reply. The existing Moda Admin-published conversation wrapper that formats normal AI and human messages supplies the presentation. The shop question, basket list or quote instruction is the value of its single `response.body` slot. BG004 prepares facts and keeps the original question. The existing wrapper system applies the active format before full-message moderation and the existing once-only sender permit.

## Context

BACKGROUND-003 establishes the immutable customer/receiving-number thread. It can return `kind: "sender-thread"` for several eligible shops or a prior shop-selection question, and `kind: "shop-route"` with a single evidenced shop. A confirmed original checkout, human or AI message can already prove one checkout on that thread. Perform shop selection using thread-local verified merchant identities and fixed questions. The shop-specific basket model can run only after one merchant has been established. The ordinary responding Commerce agent retains its one verified checkout and conversation.

The snapshot's `processRoutedInboundMessage` handles STOP and raw abuse admission before routing. Its normal text, voice and commerce-turn services all assume a conversation already exists. Its existing neutral routing guidance knows how to respond on a sender, but does not remember a question or its choices. Its moderation and commerce history readers use timestamps to determine which customer messages constitute the current objective. All three boundaries require explicit integration. In the snapshot, `RecoveryAgentContextService.getAgentContext` reads one recovery and verifies its conversation. The live Commerce host loads that same recovery, basket, customer objective and grant. Preserve that verified interface. Implement basket comparison before any call to this service or the commerce turn processor.
