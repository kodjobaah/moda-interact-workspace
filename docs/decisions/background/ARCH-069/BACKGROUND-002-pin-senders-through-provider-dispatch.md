# Pin the assigned WhatsApp sender through provider dispatch

## Objective

For every eligible Shopify or WooCommerce recovery send, the registered WhatsApp phone-number ID chosen for that checkout must appear in the actual provider request. If the platform credential names phone A and the checkout is assigned B on the same WhatsApp Business Account (WABA), use the committed permit for one submission to the customer's original recipient through `POST /{B}/messages`. A second eligible basket has its own conversation, attempt, provider receipt and credit lineage even when it shares B.

## Architecture, dependencies and scope

Parent [ARCH-069 architecture](../../../architecture/ARCH-069-whatsapp-sender-pool-and-checkout-reply-routing.md). Consume [DATABASE-001](../../database/ARCH-069/DATABASE-001-create-sender-pool-and-active-assignments.md) at the integrated submodule pin and [BACKGROUND-001](BACKGROUND-001-allocate-and-release-recovery-senders.md) at the R08 handoff contract. BG002 is one implementation task in `moda-interact-background`. All paths below are relative to that repository. The task remains pending until BG001 is architect-accepted and integrated. This is its R09 definition.

BG001 owns sender selection, assignments, expiry/release, configuration incidents, and discovery of interrupted initial attempts. BG002 calls those services from the existing workers, final send authorizations and HTTP clients. BG003 owns inbound sender recognition, STOP and provider-status processing. BG004 owns the routing model, pending questions, customer clarifications and replay of the original question to the checkout agent. Here, those consumers need only the frozen outbound identity and the explicit transport interface.
