# Materialise Moda Shopify checkbox consent at recovery and enforce stored permission

## Architecture / status

[ARCH-077](../../../architecture/ARCH-077-shopify-owned-whatsapp-checkout-consent.md). **Definition reconciled; task remains `pending`.** Implement only after accepted SHOPIFY-001, SHOPIFY-002 and BACKGROUND-001 contracts; consent is a temporary Redis choice until eligible recovery materialisation, then PostgreSQL is authoritative. Preserve existing PostgreSQL final-send checks; no per-send Redis consent reads.

## Objective and fixed ownership

Only **when an authoritative Shopify abandoned checkout becomes recoverable**, apply the latest explicit Moda checkbox selection for that checkout to the existing PostgreSQL customer/phone consent state. If there is no explicit selection, use the existing verified customer consent already in PostgreSQL. Admit recovery only with effective GRANTED permission, an eligible recipient and normal STOP/other safeguards. Later proactive sends use **existing PostgreSQL preflight and final SQL fences**, not temporary Redis consent. Do not add a new worker, queue, persistent Redis customer-preference index, database migration or native Shopify WhatsApp marketing-consent dependency.

- Shopify (`moda-interact`) owns the checkbox and the temporary Redis choice writer; BACKGROUND-001 owns verified cart-to-checkout correlation and temporary Redis lifecycle. This task reads their frozen contract and owns **recovery-time consent materialisation and outbound admission**.
- `commerce.CustomerPhone` remains the persistent current-permission authority for returning customers and subsequent recoveries. In this Shopify workflow, the existing database enum `SHOPIFY_NATIVE` is **the approved identifier for evidence established by Moda's own Shopify checkbox**. It does **not** instruct any consumer to query Shopify Messaging or `defaultPhoneNumber.whatsAppMarketingConsent`.
- `WHATSAPP_CHECKOUT_RECOVERY` purpose, decision revision/sequence, verified timestamps, matching recipient, merchant-scoped no-contact/STOP and final-send safeguards remain mandatory. `WOO_MODA_CHECKBOX` and WooCommerce API/Background paths are unchanged.
- A checkbox selection **never** writes to PostgreSQL during an ordinary cart/checkout interaction. Neither GRANT nor REVOKE is persisted when a customer completes a checkout without recoverable abandonment. This agreed deferred lifecycle applies also to returning customers.
- Do not represent a mere checkbox display, a cart/checkout webhook, a phone number in a Shopify address or a missing Redis record as a fresh opt-in or opt-out.

## Recovery-time sequence — no separate consent scheduling

1. Allow the existing merchant-defined delay, checkout/order guard, bounded Shopify verification and candidate handling to run unchanged. Only after the checkout is **confirmed abandoned and eligible for recovery** may this task materialise a new consent selection.
2. Resolve the verified `shopId + checkoutToken` and associated `cartToken` through BACKGROUND-001's separate consent namespace. Read the latest accepted **explicit** cart/checkout selection and its originating action timestamp/revision. Missing selection is distinct from an explicit unchecked REVOKE. If the Redis read/association is unavailable or indeterminate, do not infer permission; use the existing eligible retry/defer policy rather than treating an unverified result as a successful materialisation.
3. Resolve the Shopify customer from its authenticated, shop-scoped checkout identity where present. Require B001 `ASSOCIATED` and validate its `checkoutCartBinding`: **guest accepted choice** requires `MATCH`, while `MISMATCH`/`MISSING` requires an authenticated Shopify `logged_in_customer_id` recorded by S002 at action acceptance that equals the current authoritative checkout customer ID for the same shop. Otherwise return `DEFER_IDENTITY_OR_RECIPIENT` with zero SQL and no outreach. No customer merge by phone/email, no extra guessed ownership proof, and no new authentication framework. Plus uses signed checkout context instead.
4. Obtain available checkout phones from the existing authoritative Shopify abandoned-checkout lookup, including `customer.phone`, `billingAddress.phone` and `shippingAddress.phone` (in that **priority**). Select the first valid, attributable candidate, normalising with the published Shared recipient identity contract. Differing numbers are not automatically an error; an absent/invalid candidate falls through to the next source. A number known to be a third-party shipping contact is not automatically authorised. Do not attach an unrelated recipient by phone-only lookup.
5. Update/resolve the correct existing `Customer` and active `CustomerPhone` using the selected recipient; on a changed phone, preserve existing STOP/suppression history and never reformat into a new row merely to clear a STOP. A verified same-customer ongoing grant may apply to a subsequent eligible checkout/recipient, subject to the approved phone-ownership and STOP checks; do not assume a phone alone proves ownership.
6. If the checkout has an explicit Redis **GRANT** or **REVOKE**, apply it to the persistent customer consent state using the existing `SHOPIFY_NATIVE` enum, `WHATSAPP_CHECKOUT_RECOVERY` purpose and normal revision, decision-sequence and timestamp guards. The latest **successfully materialised distinct eligible checkout decision** controls the merchant/customer/recipient permission. The accepted-action timestamp/revision orders choices **within that checkout**, not durable decisions from checkouts that never became recoverable. Idempotent retries of an already-applied checkout are no-ops and cannot regrant after a newer B REVOKE. A subsequent, **separately eligible and newly materialised** GRANT may supersede B's REVOKE. Keep STOP authoritative regardless of either decision.
7. If the checkout has **no explicit selection**, read the current verified PostgreSQL customer/recipient decision. GRANTED can authorise a future recoverable checkout without a new checkbox action; UNKNOWN/REVOKED/no-contact cannot. A status read itself never creates a new decision.
8. Complete the persistent write successfully **before** treating consent as materialised or proceeding with the normal first-recovery admission. First-send reentry uses the **current stored** permission and cannot call Shopify's native WhatsApp marketing-consent provider. No `CheckoutRecovery` is created solely because consent was absent.
9. Return an explicit materialisation result to BACKGROUND-001. On successful application, B001 may remove the temporary Redis selection at the approved lifecycle point. A failed, conflicted or retryable SQL write must not be acknowledged as applied or cause premature cleanup. Completed/cancelled/ineligible checkouts clean up temporary selections through B001 without a PostgreSQL consent decision write.
10. The normal existing billing, message allowance, initial/follow-up scheduling, WhatsApp sender allocation, product/price checks and order-completion guards remain in charge. Consent capture must not itself send messages or reserve credits.

## Mandatory Cart A / Cart B materialisation and message-admission contract

**Scope and ordering**

1. **Independent recoverability before consent admission:** In `src/services/checkout-recovery/recovery-materialization.service.ts`, follow existing checkout/order/maturity/provider verification and resolve correct shop/customer and attributable phone *before* a consent-dependent initiation gate. Distinguish `RECOVERABLE` from `OUTREACH_ALLOWED`. Never turn an explicit REVOKE into `discarded-admission-denied` before the SQL decision can be written. If the checkout is paid/completed/not recoverable, do **not** write any GRANT/REVOKE. If a recipient cannot be verified, return the existing defer/no-recipient outcome; no SQL customer-level decision is fabricated.
2. **One-time SQL decision:** For a verified recoverable checkout with a latest acknowledged explicit choice, use the existing PostgreSQL `commerce.Customer` and active `commerce.CustomerPhone` row for the verified merchant/customer/canonical phone; enforce purpose `WHATSAPP_CHECKOUT_RECOVERY`, current source `SHOPIFY_NATIVE`, and existing STOP/no-contact guards. Apply GRANTED or REVOKED and update consent revision/sequence and verified time in a **short, atomic SQL transaction**; do not use Redis/provider calls while a short final-send SQL fence is held. Explicit REVOKE must commit *even though there will be no new outreach or (if existing architecture disallows it) no `CheckoutRecovery` row for B*. Do not create a `CheckoutRecovery` purely as a workaround for absent consent.
3. **Distinct checkout precedence:** Cart A's GRANT materialises and permits A's initial outreach. Cart B's later recoverable REVOKE materialises and becomes the current SQL decision. An A retry, stale worker, duplicate webhook, re-entry or crash recovery may not rematerialise A as a new GRANT afterward. The exact no-migration ordering rule is: **eligible materialisation only**, with each explicit choice retaining its immutable server-accepted `acceptedAtMs` in Redis. Lock the target active `CustomerPhone` row in the existing short PostgreSQL transaction and compare against the last materialised Shopify checkbox `whatsappConsentProviderObservedAt` (the stored accepted-action timestamp). A *strictly later* eligible accepted action may change current consent and increments the existing decision sequence/revision; an earlier action is a stale no-op. The same accepted timestamp with the same decision is an idempotent no-op; an equal timestamp with an opposite decision is a typed conflict and sends nothing. Set the provider-observed field to this verified Shopify checkbox action time, **not** to a Shopify native marketing API observation; set verified timestamps consistently with existing SQL invariants. This preserves the user's Cart A then Cart B order without making worker arrival time a new permission event. No selection from a nonrecoverable cart participates in the comparison. Crash/retry after commit must read current SQL and apply the same comparisons before any write. **Stop with `MATERIALISATION_IDEMPOTENCY_BLOCKER`** if actual existing SQL constraints or Shopify timing evidence cannot support this ordering; the agent must not choose a different authority, invent a table or deploy a weaker last-worker-wins fallback. No new decision is materialised from a mere display or completed basket.
4. **No explicit selection:** Only when marker/Redis state is positively verified as `NO_EXPLICIT_CHOICE` (or authenticated `ABSENT` under the approved contract) may a previously materialised, current merchant/customer/recipient GRANTED be reused. An indeterminate/failed Redis lookup must not be treated as a clean absence. A missing selection never writes a synthetic REVOKE or GRANT.
5. **Proactive final sends:** `src/services/recovery-conversation/recovery-stored-consent.service.ts`, `recovery-runtime-eligibility.service.ts`, `src/services/recovery-multipart/fence.ts`, `src/services/checkout-recovery/recovery-outreach-follow-up-processor.service.ts` and the outbound permit path must evaluate **current SQL GRANTED** and independent STOP at the existing final-send fence for *all customer-unsolicited recovery messages*: first outreach, retries not yet accepted, scheduled follow-ups and proactive multipart portions. After B SQL REVOKED, suppress any such not-yet-provider-accepted A follow-up and new C outreach, even though A's first message was delivered and the recovery/conversation remains open. Credit reservation/compensation and sender idempotency remain unchanged.
6. **Customer-initiated service replies:** Keep A's existing recovery conversation and message history intact. An actual customer reply/inbound may be answered by current AI/human responders through the existing conversation route under the 24-hour service window, moderation, WhatsApp/provider admission and STOP policy. Do not use the proactive-consent fence as a blanket denial for a *response* to inbound; do not treat opening a 24-hour window as consent for an unsolicited follow-up. No automatic `GRANTED` reset, new outreach attempt, new conversation or additional proactive credit occurs solely because the customer replies.
7. **STOP:** Existing authoritative STOP handling remains immediate and independent of checkbox choices. A checkbox REVOKE is **not** STOP and has **no immediate or pre-recovery suppressive effect** on SQL or A's ongoing proactive schedule. Do not add a new Redis preflight for pending REVOKE.

**Required typed B002 results:** `NOT_RECOVERABLE_TERMINAL` (cleanup with zero SQL), `DEFER_IDENTITY_OR_RECIPIENT` (no SQL/no send), `DEFER_CORRELATION_OR_REDIS_UNVERIFIED` (no SQL/no send), `NO_EXPLICIT_CHOICE` (SQL read-only), `MATERIALISED_GRANTED` (one SQL update then normal admission), `MATERIALISED_REVOKED` (one SQL update and **no** new proactive outreach), `ALREADY_MATERIALISED` (no SQL rewrite; current SQL decides proactive admission), `BLOCKED_STOP`, `MATERIALISATION_FAILURE` (no Redis cleanup/false acknowledgement). Adapt these inside the existing return/reporting boundary; do not add a worker, new table or independent scheduler.

**Implementation is authorised after B001 acceptance, not after repeating S001.** B002 must implement the prescribed SQL row lock and immutable accepted-action timestamp comparison and prove idempotence before enabling consent writes. If actual SQL constraints make this exact rule impossible, fail with `MATERIALISATION_IDEMPOTENCY_BLOCKER` and request a new architect decision; do not invent a migration/alternative.

**Concrete fixtures to prove before claiming implementation complete:** (A) A GRANT selected but not recoverable -> zero SQL; (B) A recoverable -> SQL GRANTED, exactly one initial outreach; (C) B REVOKE selected -> SQL still GRANTED, A follow-up still subject to existing consent; (D) B paid -> zero new SQL, A SQL GRANTED unchanged; (E) B recoverable -> SQL REVOKED, no B outreach and any A unsent follow-up denied; (F) actual customer replies to A -> 24-hour service AI/human reply permitted under existing policies; (G) A delayed duplicate/re-entry after B -> B REVOKED stays; (H) C no new choice -> no proactive; (I) C distinct recoverable explicit GRANT -> SQL GRANTED subject to STOP; (J) STOP at any point -> existing immediate suppression. Include crash injection after SQL commit before Redis consumed acknowledgement.

## Re-entry, provider dispatch and STOP

- **Do not use Redis as a consent authority after successful materialisation.** Subsequent initial-send retries, follow-ups and proactive provider sends read current `CustomerPhone` permission using the existing preflight and short PostgreSQL final-send transaction.
- Preserve `checkFinalStoredRecoveryConsent` and its exact shop/customer/active phone, canonical recipient, `SHOPIFY_NATIVE`, purpose, decision, verified timestamps, consent/no-contact revisions and STOP checks. No Redis network operations are added inside that SQL transaction, and no replacement distributed Redis/SQL dispatch lock is required.
- Update the Shopify consent admission and materialisation callers so `SHOPIFY_NATIVE` rows are written from Moda-verified Shopify checkbox decisions **without querying** `defaultPhoneNumber.whatsAppMarketingConsent`. Do not simply remove or bypass a final stored-consent fence.
- A current PostgreSQL REVOKED/UNKNOWN decision, a newer materialised withdrawal or any local STOP prevents future **proactive** sends (including A's unsent scheduled follow-up). Customer-originated replies, merchant human handover and WhatsApp 24-hour customer-service policies **remain independently admitted** subject to their existing safeguards and must not inherit this proactive-only consent gate. A scheduled follow-up is still proactive even inside an open 24-hour window.
- Existing order-completion fences, suppression, credit reservation/release and ARCH-076 sender assignment/idempotency remain unchanged. A send already accepted by the provider is not recallable. Never claim a transient unmaterialised Redis selection has changed the persistent state of earlier recoveries.
- **Preproduction retirement:** Remove the obsolete native Shopify provider-sync processing in B002, coordinated with S006 removal of the Shopify webhook producer. No legacy-job compatibility, replay or data migration is required. Keep existing cart/checkout/order worker queue and unrelated job processing unchanged; any preproduction cleanup is a separate scoped environment operation.

## Redis and database boundaries

- Read only versioned ARCH-077 consent keys frozen in S001/B001. **Never** alter `pending-recovery:index:checkout:*`, `pending-recovery:index:cart:*`, `pending-recovery:index:shop:*`, `pending-recovery:lock:*`, `pending-recovery:order-completed:*`, BullMQ job payloads, job IDs, queue delays or TTLs for consent storage.
- Do not introduce permanent Redis customer consent/history, new database tables, enums, fields, migrations, new recovery queues, secondary Shopify consent API service or WooCommerce application/API changes.
- Keep database access limited to existing recipient/customer, consent and admission operations; avoid duplicate shop/customer queries, diagnostic-only SELECTs and long transactions containing Shopify API/Redis network calls.
- Log the original safe Redis/Shopify/Prisma error message and relevant provider details at the server boundary with secret/PII redaction; return fixed, non-sensitive failure codes. A Redis failure or missing evidence is not a valid consent decision.

## Required tests and acceptance

- New authenticated Shopify customer with an explicit GRANT: abandoned checkout verified, recipient resolved, stored consent GRANTED, normal recovery admitted.
- Existing customer GRANTED and **no new checkbox action**: future abandoned checkout uses stored permission without minting another GRANT. Existing REVOKED/UNKNOWN denies.
- Existing customer GRANTED, explicit REVOKE on a new cart, checkout **becomes recoverable**: newer REVOKE is materialised before admission and blocks outreach. The same new cart **completes normally**: no SQL update, no recovery, temporary consent cleaned by B001, per approved lifecycle.
- Newer explicit GRANT after earlier REVOKE is accepted; older delayed GRANT processed after a newer REVOKE is rejected as stale. Parallel eligible checkouts for one customer remain correctly ordered across retries.
- `customer.phone = null`, billing and shipping phones present: billing used; valid customer phone takes precedence over different billing phone; invalid customer phone falls back to billing; no false ambiguity simply because numbers differ. Known unrelated shipping recipient is denied.
- Changed recipient, Shopify customer identity/phone mismatch, unverified guest association, missing Redis state, Redis outage, duplicate action, conflicted association, failed SQL write, aborted eligibility and premature cleanup all fail closed appropriately.
- Existing STOP across consent/recipient changes; no-contact revision and final SQL fence preserve suppression. Existing initial/reentry/retry/follow-up/multipart paths use PostgreSQL after materialisation; no native Shopify marketing-consent API read.
- Order completion, merchant-configured maturity, bounded Shopify retries, credit compensation, ARCH-076 sender allocation and WooCommerce regression stay unchanged.
- Execute disposable PostgreSQL + Redis integration tests with real concurrent accepted decisions and rejected stale replay, plus Shopify/Meta mocked boundary tests; verify exact task worktree/commit/submodule pin and container cleanup. Do not present mocked tests as real provider evidence.

**Stop conditions:** Abort **the affected consent materialisation/outreach path** and report an architect blocker if B001/B002 cannot verify guest cart-token equality or signed same-customer identity, if a newly accepted consent decision cannot be persisted under the existing `SHOPIFY_NATIVE` constraints without database changes, if obsolete native provider sync processing remains active at new checkbox activation, if old grants supersede newer withdrawals, or if any proactive final-send path can bypass the current stored-consent/STOP fence. Do not weaken the existing SQL constraints or WooCommerce policy to make tests pass.
