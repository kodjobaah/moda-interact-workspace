# ARCH-053-BACKGROUND-004 — Preserve checkout-vs-alternative target in confirmed outreach receipt

## Architecture

`ARCH-053` — `docs/architecture/ARCH-053-woocommerce-checkout-recovery-links-and-cart-restoration.md`, coordinated by `moda_architect`. Defined but **not materialised**; no branch, worktree, commit, push or acceptance is claimed.

## Objective

Make the **already persisted, confirmed initial WhatsApp message** unambiguously identify whether its offered discount was for the abandoned checkout or a separately promoted product. This is a narrow compatibility bridge for ARCH-053 restoration; ARCH-052 continues to own dynamic discovery, eligibility proof and offer choice.

## Context

In the inspected Background implementation, `prepared-template-send.ts` declares `RecoveryOfferPromise` with `kind`, provider ID and optional code. `prepareAutomatedTemplateInput()` serialises that object into `ConversationMessage.content` (`contract: 'moda.whatsapp.automated-template-parameters.v1'`). The initial attempt's `outboundMessageId` references the confirmed message. ARCH-052-BACKGROUND-008 extends the send path for `promotionTarget: CHECKOUT | ALTERNATIVE_PRODUCT`, but the existing baseline does **not prove** that the receipt always records the target. API-003 must not treat an untagged CODE_OFFER as inherently applicable to the checkout.

## Scope

In `moda-interact-background`, **only if this is not already correctly satisfied in accepted ARCH-052-BACKGROUND-008**:

- `src/services/recovery-template-integration/prepared-template-send.ts`: add required `promotionTarget: 'CHECKOUT'|'ALTERNATIVE_PRODUCT'` on positive `RecoveryOfferPromise` variants generated by the ARCH-052 initial send; preserve existing verified alternative-product identifiers and the `NO_OFFER` variant.
- `src/services/recovery-template-integration/automated-recovery-template.service.ts`: map the trusted approved target, kind, provider discount ID and verified code to the promise; adjust the existing `previousPromise()` parser to retain target for follow-up checks, not to guess it from untrusted text.
- `src/services/conversation-moderation/automated-template-input.ts`: maintain the existing serialised `recoveryPromise` receipt and no new `sentOffer` table/field; add only necessary type/contract validation for target-vs-template purpose. Do not introduce a competing message format.
- Focused tests alongside these modules, e.g. `src/services/recovery-template-integration/automated-recovery-template.test.ts` or their existing test location, covering exact persisted content and follow-up parity.

If accepted ARCH-052-BACKGROUND-008 already proves the exact target-bearing confirmed receipt, this task becomes **evidence-only**: rerun the narrowly scoped receipt/follow-up assertions, record the accepted implementation commit and results in its Completion Report, and return for architect acceptance **as Complete without source churn**.
