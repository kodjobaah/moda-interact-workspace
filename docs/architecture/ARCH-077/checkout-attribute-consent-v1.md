# ARCH-077 — Shopify checkout-attribute consent receipt v1

**Architecture decision (17 November 2026).** Supersedes ARCH-077 temporary Redis GRANT/REVOKE, `m1_` cart marker, marker-to-checkout association, cart/marker/link TTL, new consent-specific BullMQ jobs and their cleanup. **Source-of-truth at recoverability:** the authoritative Shopify `AbandonedCheckout.customAttributes`, fetched in the existing provider verification operation. **Durable authority after eligible materialisation:** existing PostgreSQL `CustomerPhone`. The completed S001 cart-to-checkout marker experiment remains recorded feasibility evidence, *not* a requirement to retain the marker in production.

## Immutable policy, supported storefront placements

1. Exactly one merchant-plan-specific customer-facing control: non-Plus cart Theme App Block (S003) **or** eligible Plus `purchase.checkout.contact.render-after` Checkout UI Extension (S004), never both. Shopify merchant plan/availability gates must be tested; on unsupported or accelerated paths hide only Moda's control without blocking checkout.
2. The checkbox English wording is **exactly** `Send me WhatsApp shopping updates, reminders and offers.` with the established 20-locale Shopify translation meaning. An initial checked display from previously materialised PostgreSQL permission does **not** create a new receipt. Only an explicit click/check/uncheck issues a receipt.
3. An acknowledged GRANT or REVOKE is a **checkout-scoped selection in Shopify's single attribute**, not immediately effective merchant permission. No new PostgreSQL decision or outbound suppression until that checkout is independently recoverable. A normal paid/completed/definitively ineligible checkout causes no materialisation. STOP retains its independently immediate effect.
4. Once a recoverable checkout's REVOKE commits to PostgreSQL, it blocks **all new proactive outreach** to the same merchant/customer/recipient scope, including unsent A follow-ups, but does not close an earlier conversation or prohibit legitimate customer-initiated AI/human replies admitted under the 24-hour WhatsApp service window, moderation, routing and STOP rules. Cart A GRANT, Cart B REVOKE, Cart B paid versus recoverable, and stale A retry semantics remain mandatory.

## One Shopify attribute and signed wire contract

- **Attribute name (both plans, exactly one):** `moda_wa_consent_v1` (20 characters; never a second GRANT/REVOKE or marker attribute). The previous `moda_s001_probe` was diagnostic only; no production writes to it. `moda_cart_correlation_v1` is obsolete for the consent feature; do not emit it in new storefront code.
- **Attribute value:** ASCII `v1.<shopId>.<kind>.<bindingDigest>.<decision>.<disclosureVersion>.<locale>.<acceptedAt>.<customerId>.<mac>`, with 10 dot-separated tokens and no whitespace. The MAC is HMAC-SHA256 over the entire ASCII prefix preceding `.<mac>`; use unpadded base64url for the 32-byte MAC. Signing key comes from **one Shopify/Background shared deployment secret** `SHOPIFY_CONSENT_RECEIPT_KEY_V1`, exactly 32 cryptographically random bytes encoded as unpadded base64url. Both sides decode/validate that key at startup; never log it, store it in Shopify, or derive it from customer data. Do not introduce Redis, a signing service, or a new database model for key management.
- **`shopId`:** internally resolved merchant/shop CUID matching `^[a-z0-9]{20,40}$` (not client-supplied). **`kind`:** `c` for non-Plus cart; `x` for Plus checkout. **`bindingDigest`:** unpadded base64url SHA-256 of the UTF-8 bytes of the selected verified Shopify base cart token (`c`, remove any `?` suffix) or Shopify checkout token (`x`); exactly 43 base64url characters. **`decision`:** `G` or `R` (GRANT/REVOKE). **`disclosureVersion`:** ASCII decimal `1` for this version, even if the displayed translation differs. **`locale`:** canonical verified shopper BCP-47 locale 2–35 characters `[A-Za-z0-9-]`, no dots. **`acceptedAt`:** positive Unix epoch **seconds** from server clock, not browser clock. **`customerId`:** verified signed Shopify numeric customer ID (`^[1-9][0-9]{0,19}$`) if present, otherwise literal `-` for guest. **`mac`:** exactly 43 unpadded base64url characters.
- **Canonical encoding:** construct the prefix from the above fields in that exact order and sign its raw UTF-8 bytes with `createHmac('sha256', key)`. On verification split strictly into ten components, reject extra/missing fields, noncanonical base64url, invalid types/lengths, unrecognised locale/version, duplicate checkout attribute keys, empty values or excessive length (maximum **512 ASCII bytes**). Recompute MAC over the exact raw prefix and compare decoded 32-byte MACs with `timingSafeEqual`; never trust an attribute's unsigned shop, customer, source or decision before signature verification. Receipt uses **no expiry based on inactivity or merchant-configured recovery lifetime**; acceptedAt is evidence only, not a Redis TTL. Reject timestamps more than five minutes in the future, allow historic valid receipts until Shopify's applicable checkout/recovery eligibility policy expires. No arbitrary 48-hour restriction.
- **Deterministic test vector (synthetic; never use the test key for deployment):** 32-byte signing key `000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f` (hex), equivalently base64url `AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8`; `shopId=cmwexample000000000000001`; base cart token `test-cart-token-001`; `kind=c`, `decision=G`, `disclosureVersion=1`, `locale=en-GB`, `acceptedAt=1794900000`, `customerId=-`. Expected bindingDigest `CqNn7cXy0D3FFItDIoTupWsTV3AK9KiMvHKWdQB1pG8`. Expected **full receipt** `v1.cmwexample000000000000001.c.CqNn7cXy0D3FFItDIoTupWsTV3AK9KiMvHKWdQB1pG8.G.1.en-GB.1794900000.-.4ksjVFSbs2syVaE59VAR7KoyiX6RzcjDpGkKDMriSxE` (141 ASCII characters). Both Shopify and Background verifiers must reproduce/accept this vector and fail if a single byte of the signed prefix changes.
- **One record, last snapshot:** the *single currently present valid receipt* in the authoritative abandoned checkout is the checkout's explicit selection. Each deliberate selection creates a new receipt and atomically **replaces the same attribute key** using the Shopify API; no GRANT/REVOKE action log and no timestamp-based lookup for prior receipts. A Shopify attribute removal is absence, not REVOKE. Duplicate `moda_wa_consent_v1` keys, a malformed/invalid signature, conflicting data or indeterminate provider lookup **fail closed**; never convert to GRANTED. An unsigned plain `GRANT` or `REVOKE` is not usable.
- **Accepted limitation:** this *stateless* design cannot detect reinstatement of an older valid signed receipt into the **same** checkout attribute. `acceptedAt` does not prevent same-checkout replay and must **not** be presented as a monotonic current-action guarantee. This is an explicitly scoped security/product tradeoff in the approved minimal architecture. Cross-shop and cross-checkout token copying must still fail binding verification. If preventing same-checkout replay becomes mandatory, obtain a **new** architect decision before adding state; agents are not authorised to invent Redis history or a database table.
- **Attribution:** an authenticated App Proxy identifies the shop and, optionally, the signed logged-in Shopify customer; it does *not* independently prove guest/cart ownership. Checkout extension requests must use signed Shopify checkout session tokens for shop/customer context. The browser-supplied cart/checkout token is only a locator until independently matched at recoverability. Server issuance is not proof that only Moda's checkbox could invoke the endpoint. Never state otherwise in audit/test reports.

## Issuance and merchant-plan routes

**Shopify-owned receipt issuer (`moda-interact` / S002):** replace `app/services/shopify-consent/shopify-consent.server.ts` Redis-dependent prepare/status/choice service with stateless `app/services/shopify-consent/consent-receipt.server.ts`. Implement `issueConsentReceipt`, `verifyConsentReceipt` (share exact pure verifier contract with Background by accepted owned source, not by a new mandatory Shared package release), and `readReturningShopperConsentStatus`. Keep existing server logging/redaction. Remove obsolete `marker.ts` and Redis consent integration tests; migrate relevant tests to receipt unit and route tests. No new Redis, table, queue or database migration.

- **Non-Plus:** reuse `app/routes/shopify/consent/route.ts`, `app/routes.ts`, and the single configured `[app_proxy]`. `GET cart/status` reads existing PostgreSQL consent for verified signed `logged_in_customer_id` (or returns unchecked for guest); `POST cart/receipt` receives an explicit choice, current Ajax base cart token and displayed locale. Authenticate via `authenticate.public.appProxy` and enforce signed shop/timestamp, freshness ±300s, approved proxy prefix, store scope, Origin is a browser diagnostic, **not** authentication: accept supported HTTPS custom storefront domains after Shopify SDK signature/shop verification; reject a malformed/non-HTTPS Origin when present, but do not require equality to the shop's `.myshopify.com` domain, JSON and bounded body. Never trust supplied shop/customer IDs. Return the signed receipt, which the **browser writes** using locale-aware `/cart/update.js` and verifies by readback; the backend does not impersonate the browser to mutate a cart. If verify fails or no cart token is available, no receipt is acknowledged and checkout remains usable. Do not retain the receipt server-side.
- **Plus:** `POST checkout/receipt` is an independent, non-proxy resource route under `app/routes.ts`; authenticate a Shopify Checkout UI Extension `shopify.sessionToken.get()` JWT via the existing Shopify SDK's checkout authentication capability, verify its shop/customer claims and verify the checkoutToken locator is available. The extension supplies `checkoutToken`, choice and shopper locale in a bounded JSON body; server signs kind `x` with that checkout token binding. Use `shopify.applyAttributeChange({type:'updateAttribute', key:'moda_wa_consent_v1', value:receipt})` and verify success/readback; require `instructions.attributes.canUpdateAttributes` and supported target. Missing checkoutToken, no verified session, unsupported target, network access denied or accelerated checkout => **hide only Moda control**, never block payment. No cart marker or cart App Block is enabled for Plus. `authenticate.public.checkout` or supported installed SDK equivalent must actually be proven at runtime; do not invent JWT claim semantics.
- **Existing SQL status:** a returning, verified shop+Shopify-customer reads the current `CustomerPhone` decision and STOP/no-contact status for *display only*. Existing signed current-checkout receipt takes precedence for current control state; a read/render/unchecked default is not an action. Guests never receive previous customer consent from email/phone similarity.
- **Endpoint failure:** silent shopper failure, preserve last acknowledged display or hide control, never report unacknowledged writes as accepted, never block cart/checkout; server logs original useful SDK/provider errors with secret/PII redaction.

## Background decision path and exact binding checks

1. Keep current authenticated webhook, BullMQ event types, pending-candidate indexes, queue names/IDs/delays and existing Shopify abandoned-checkout lookup. **Do not** add `note_attributes` or a signed receipt to the queue payload. The previously accepted SHARED-001 marker fields remain optional and unused; do not undo the completed Shared task or force a package republish solely for this change.
2. At the *existing* authoritative Shopify abandoned-checkout fetch (`AbandonedCheckout.customAttributes {key value}`), select the unique `moda_wa_consent_v1` attribute and validate the signed value **within the same fetch**. No separate lookup to retrieve consent, no Redis consent read and no extra webhook correlation query.
3. Verify signed `shopId` against the *existing authenticated shop*, `kind` against the shop's approved placement (non-Plus `c`, Plus `x`), and receipt's signed customer ID against the verified Shopify customer ID at recovery. For anonymous `-`, do not infer identity from phone/email alone. Recipient must still be attributable to the consenting customer under the existing customer phone -> billing phone -> shipping phone rule.
4. Verify receipt binding **against the exact authenticated Shopify checkout token (Plus) or authenticated event cart token (non-Plus)** already available from the existing checkout candidate ingestion. GraphQL `AbandonedCheckout` does not itself expose the cart token; do not pretend it does. If the necessary event token is absent, changed, ambiguous or cannot be linked to the authoritative abandoned checkout, return a typed verification denial and **do not** materialise or send. This intentionally excludes some cart-regeneration flows previously seen in testing; do not silently accept based on matching items, address, email or timestamp. No alternative marker may be introduced without architect review.
5. Independently prove the checkout has become recoverable using existing maturity, completion, payment and cancellation gates **before** examining permission or creating `CheckoutRecovery`. Only then materialise a verified explicit GRANT/REVOKE in existing PostgreSQL `CustomerPhone`. A recoverable REVOKE is applied even if no outbound recovery record/message will be created. A normal completed checkout contributes no new SQL decision. No receipt means no new decision: reuse prior verified SQL consent only if current customer/recipient binding and STOP permit it.
6. Recheck current SQL stored consent and STOP at every proactive final outbound send, including initial outreach, unsent retry, follow-up, multipart; no extra Redis check. A valid Cart A initial message can remain, but after recoverable Cart B REVOKE commits, no new unsolicited Cart A follow-up may start. Existing customer-initiated AI/human service replies remain eligible under their separate policies. Preserve existing credit and ARCH-076 sender guarantees.
7. **Idempotency / older worker replay:** an already-applied checkout decision must never reapply its older GRANT after newer Cart B REVOKE. Use existing durable checkout/recovery identity and transaction protections only; if the existing database cannot distinguish a decision already materialised from one not yet materialised, B002 must stop with `MATERIALISATION_IDEMPOTENCY_BLOCKER` for architect review. No speculative new column/table, timestamp-only decision sort or distributed lock.

- The earlier successful **non-Plus** test proved `moda_s001_probe` survived Ajax cart -> authenticated checkout webhooks -> `AbandonedCheckout.customAttributes` (SHA-256 prefix `ef5dbf7582291225`); it did **not** prove server-signing, integrity, guest ownership or the **Plus** extension write/read path. Document this distinction.
- Verify standard cart actual receipt survives into GraphQL and matches the correct candidate token; verify the Plus extension authenticated issuer/readback and authoritative GraphQL receipt. Test accelerated checkout non-support, updated values, copied receipts across shops/checkouts, invalid MAC, missing/duplicate attrs, native provider read retirement, guest/custom-domain and 20 locales.

Keep two proactive messages per recovery, STOP and billing policies unchanged.
