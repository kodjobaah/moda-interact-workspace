# ARCH-077 — Shopify checkout-attribute consent receipt v1

**Architecture decision (17 November 2026).** Supersedes ARCH-077 temporary Redis GRANT/REVOKE, `m1_` cart marker, marker-to-checkout association, cart/marker/link TTL, new consent-specific BullMQ jobs and their cleanup. **Source-of-truth at recoverability:** the authoritative Shopify `AbandonedCheckout.customAttributes`, fetched in the existing provider verification operation. **Durable authority after eligible materialisation:** existing PostgreSQL `CustomerPhone`. The completed S001 cart-to-checkout marker experiment remains recorded feasibility evidence, *not* a requirement to retain the marker in production.

## Immutable policy, supported storefront placements

1. Exactly one merchant-plan-specific customer-facing control: non-Plus cart Theme App Block (S003) **or** eligible Plus `purchase.checkout.contact.render-after` Checkout UI Extension (S004), never both. Shopify merchant plan/availability gates must be tested; on unsupported or accelerated paths hide only Moda's control without blocking checkout.
2. The checkbox English wording is **exactly** `Send me WhatsApp shopping updates, reminders and offers.` with the established 20-locale Shopify translation meaning. An initial checked display from previously materialised PostgreSQL permission does **not** create a new receipt. Only an explicit click/check/uncheck issues a receipt.
3. An acknowledged GRANT or REVOKE is a **checkout-scoped selection in Shopify's single attribute**, not immediately effective merchant permission. No new PostgreSQL decision or outbound suppression until that checkout is independently recoverable. A normal paid/completed/definitively ineligible checkout causes no materialisation. STOP retains its independently immediate effect.
4. Once a recoverable checkout's REVOKE commits to PostgreSQL, it blocks **all new proactive outreach** to the same merchant/customer/recipient scope, including unsent A follow-ups, but does not close an earlier conversation or prohibit legitimate customer-initiated AI/human replies admitted under the 24-hour WhatsApp service window, moderation, routing and STOP rules. Cart A GRANT, Cart B REVOKE, Cart B paid versus recoverable, and stale A retry semantics remain mandatory.

## One Shopify attribute and Shared-authenticated receipt v1 contract (reconciled 17 November 2026)

- **Attribute name (both plans, only one):** `moda_wa_consent_v1`. The prior `moda_s001_probe` and `moda_cart_correlation_v1` are diagnostic/obsolete; no production writes to either. A plain unsigned `GRANT` or `REVOKE` is invalid.
- **Security implementation and configuration:** Reuse only the published Node entrypoint `@modainteract/moda-interact-shared/security/credentials/node`: `parseCredentialKeyring`, `resolveActiveCredentialKey`, `encryptCredential`, `decryptCredential`, `CredentialEnvelope`. Both services use their existing `MODA_ENCRYPTION_KEYS_JSON`; **Shopify writer** also uses `MODA_ENCRYPTION_ACTIVE_KEY_ID` to select the encrypting key. Decryption selects the key from `CredentialEnvelope.keyId` in the same keyring, not the current active-key setting. The keyring's standard base64, ID validation, AES-256-GCM nonce/tag sizes and rotation/error semantics come from Shared unchanged. **Do not add `SHOPIFY_CONSENT_RECEIPT_KEY_V1`, another secret, per-merchant key, independent key-rotation algorithm, local AES/HMAC or generic cryptographic wrapper.** Missing/invalid configuration fails closed for receipt issuance/verification; checkout remains functional with no claimed Moda selection.
- **Receipt ASCII format (exact, replaces unreleased HMAC value):** `v1.<keyId>.<nonce>.<ciphertext>.<authTag>` (exactly **five dot-separated ASCII fields**). `keyId` is the existing Shared envelope key ID, while `nonce`, `ciphertext` and `authTag` are canonical unpadded base64url of the Shared envelope's **12-byte nonce**, nonempty ciphertext and **16-byte authTag**. No JSON wrapper around the envelope and no additional fields or whitespace. Enforce ASCII and maximum **512 bytes** for the complete Shopify attribute; reject noncanonical base64url, malformed UTF-8/JSON, wrong number of fields/extra fields, invalid key ID, nonce/tag length and overlong values. Decode to Shared's `CredentialEnvelope` with `Uint8Array` binary members. This serialization is domain framing only: `encryptCredential`/`decryptCredential` still own authenticated encryption, key selection and error semantics.
- **Plaintext bytes before encryption:** exactly `JSON.stringify([1, shopId, kind, bindingDigest, decision, "1", locale, acceptedAt, customerId])` with array order preserved. `shopId` is internally authenticated merchant/shop CUID matching `^[a-z0-9]{20,40}$`; `kind` is `c` for non-Plus cart or `x` for Plus checkout; `bindingDigest` is canonical 43-character unpadded base64url SHA-256 of the UTF-8 **base cart token** (`c`, strip its query suffix) or trusted checkout token (`x`). `decision` is `G`/`R`; disclosure version literal `"1"`; `locale` is canonical verified BCP-47 2–35 characters `[A-Za-z0-9-]`; `acceptedAt` is server-generated positive Unix epoch **seconds**; `customerId` is a verified signed Shopify numeric customer ID (`^[1-9][0-9]{0,19}$`) or `"-"` for guest. No browser-supplied merchant/customer ID or consent time is authoritative.
- **AAD bytes (exact for Shopify writer and Background reader):** `JSON.stringify(["moda-shopify-wa-consent", 1, expectedShopId, expectedKind, expectedBindingDigest])` passed as UTF-8 to Shared `encryptCredential`/`decryptCredential`. `expectedShopId` comes from authenticated shop context; `expectedKind` from the known exclusive plan placement; `expectedBindingDigest` from the trusted cart token of the checkout event (`c`) or checkout token (`x`). **Do not compute verification AAD from decoded receipt claims.** For a mismatched shop, plan kind or checkout/cart binding, authentication fails. After successful decryption parse and validate all nine plaintext array members and require that plaintext shop/kind/digest equal the same trusted expected inputs. The current GraphQL abandoned-checkout API does not itself supply the cart token; use only the existing independently authenticated candidate event token, never infer by matching basket/customer/date.
- **Validation:** decrypt using the published Shared Node AEAD. Reject missing, duplicate or malformed attribute values, unknown/deleted key ID, bad tag, wrong AAD, invalid claims/locale/version, `acceptedAt` more than five minutes in the future, token/customer/shop mismatch and unsupported plan/placement. No 48-hour TTL: past receipts remain eligible only while the **existing authoritative checkout recoverability policy** allows evaluation. A missing receipt means no *new* explicit choice (previous materialised PostgreSQL consent is evaluated separately under normal controls); do not manufacture GRANT. Never emit decrypted plaintext claims, Shopify authentication tokens or key material to logs. Outside the narrowly defined synthetic-data-only `test`/`development` Shopify GraphQL diagnostic exception below, also never emit a complete encrypted receipt. The exception permits only the opaque encrypted attribute as returned by Shopify, not decrypted claims or credential material.
- **One latest snapshot:** each deliberate explicit check/uncheck issues a new encrypted receipt and replaces the **same** Shopify attribute; initial render, existing SQL permission display and absent attribute produce no action. `acceptedAt` is informational, not a database decision order. The stateless model cannot detect restoring a formerly valid encrypted receipt into the **same** checkout; this is the accepted limitation, not evidence of replay prevention. Cross-shop/cross-checkout copied receipts fail AAD and binding checks. If stricter same-checkout replay prevention is required, return a new architect decision; do not add a Redis preference/history store.
- **Key rotation:** Shared `CredentialEnvelope.keyId` and `decryptCredential` are authoritative. Issuance uses the configured active key; a checkout receipt encrypted before rotation remains readable only while its old key remains in `MODA_ENCRYPTION_KEYS_JSON` in Background. This is an operational retention requirement, **not a new rotation mechanism**. Missing old keys fail closed. Existing Shared keyring rotation unit tests are authoritative for the generic mechanism; ARCH-077 needs only a targeted issuing-on-new-key/reading-old-receipt compatibility test and shared writer/reader fixture with the exact AAD above. No deterministic ciphertext fixture is required from a randomized-nonce AES-GCM API; test exact *AAD/plaintext bytes*, both-side round-trip, and tamper failures.
- **Attribution:** a signed Shopify App Proxy authenticates shop context and optionally the logged-in customer, not arbitrary guest/cart ownership. Checkout extension issuer uses verified Shopify session-token claims. The client-supplied token is a locator that must independently match the authoritative recovery candidate. No receipt proves only Moda's checkbox could have invoked the endpoint; never make that claim.

## Issuance and merchant-plan routes

**Shopify-owned receipt issuer (`moda-interact` / S002):** replace `app/services/shopify-consent/shopify-consent.server.ts` Redis-dependent prepare/status/choice service with stateless `app/services/shopify-consent/consent-receipt.server.ts`. Implement `issueConsentReceipt`, `verifyConsentReceipt` (consume canonical Shared AEAD mechanics; use the exact receipt-specific envelope/plaintext/AAD contract above in Background, without copying generic encryption implementations), and `readReturningShopperConsentStatus`. Keep existing server logging/redaction. Remove obsolete `marker.ts` and Redis consent integration tests; migrate relevant tests to receipt unit and route tests. No new Redis, table, queue or database migration.

- **Non-Plus:** reuse `app/routes/shopify/consent/route.ts`, `app/routes.ts`, and the single configured `[app_proxy]`. `GET cart/status` reads existing PostgreSQL consent for verified signed `logged_in_customer_id` (or returns unchecked for guest); `POST cart/receipt` receives an explicit choice, current Ajax base cart token and displayed locale. Authenticate via `authenticate.public.appProxy` and enforce signed shop/timestamp, freshness ±300s, approved proxy prefix, store scope, Origin is a browser diagnostic, **not** authentication: accept supported HTTPS custom storefront domains after Shopify SDK signature/shop verification; reject a malformed/non-HTTPS Origin when present, but do not require equality to the shop's `.myshopify.com` domain, JSON and bounded body. Never trust supplied shop/customer IDs. Return the authenticated receipt, which the **browser writes** using locale-aware `/cart/update.js` and verifies by readback; the backend does not impersonate the browser to mutate a cart. If verify fails or no cart token is available, no receipt is acknowledged and checkout remains usable. Do not retain the receipt server-side.
- **Plus:** `POST checkout/receipt` is an independent, non-proxy resource route under `app/routes.ts`; authenticate a Shopify Checkout UI Extension `shopify.sessionToken.get()` JWT via the existing Shopify SDK's checkout authentication capability, verify its shop/customer claims and verify the checkoutToken locator is available. The extension supplies `checkoutToken`, choice and shopper locale in a bounded JSON body; server signs kind `x` with that checkout token binding. Use `shopify.applyAttributeChange({type:'updateAttribute', key:'moda_wa_consent_v1', value:receipt})` and verify success/readback; require `instructions.attributes.canUpdateAttributes` and supported target. Missing checkoutToken, no verified session, unsupported target, network access denied or accelerated checkout => **hide only Moda control**, never block payment. No cart marker or cart App Block is enabled for Plus. `authenticate.public.checkout` or supported installed SDK equivalent must actually be proven at runtime; do not invent JWT claim semantics.
- **Existing SQL status:** a returning, verified shop+Shopify-customer reads the current `CustomerPhone` decision and STOP/no-contact status for *display only*. Existing signed current-checkout receipt takes precedence for current control state; a read/render/unchecked default is not an action. Guests never receive previous customer consent from email/phone similarity.
- **Endpoint failure:** silent shopper failure, preserve last acknowledged display or hide control, never report unacknowledged writes as accepted, never block cart/checkout; server logs original useful SDK/provider errors with secret/PII redaction.

## Background decision path and exact binding checks

1. Keep current authenticated webhook, BullMQ event types, pending-candidate indexes, queue names/IDs/delays and existing Shopify abandoned-checkout lookup. **Do not** add `note_attributes` or a signed receipt to the queue payload. The previously accepted SHARED-001 marker fields remain optional and unused; do not undo the completed Shared task or force a package republish solely for this change.
2. At the *existing* authoritative Shopify abandoned-checkout fetch (`AbandonedCheckout.customAttributes {key value}`), select the unique `moda_wa_consent_v1` attribute and validate the signed value **within the same fetch**. No separate lookup to retrieve consent, no Redis consent read and no extra webhook correlation query.
3. Verify signed `shopId` against the *existing authenticated shop*, `kind` against the shop's approved placement (non-Plus `c`, Plus `x`), and receipt's signed customer ID against the verified Shopify customer ID at recovery. For anonymous `-`, do not infer identity from phone/email alone. Recipient must still be attributable to the consenting customer under the existing customer phone -> billing phone -> shipping phone rule.
4. Verify receipt binding **against the exact authenticated Shopify checkout token (Plus) or authenticated event cart token (non-Plus)** already available from the existing checkout candidate ingestion. GraphQL `AbandonedCheckout` does not itself expose the cart token; do not pretend it does. If the necessary event token is absent, changed, ambiguous or cannot be linked to the authoritative abandoned checkout, return a typed verification denial and **do not** materialise or send. This intentionally excludes some cart-regeneration flows previously seen in testing; do not silently accept based on matching items, address, email or timestamp. No alternative marker may be introduced without architect review.
5. Independently prove the checkout has become recoverable using existing maturity, completion, payment and cancellation gates **before** examining permission or creating `CheckoutRecovery`. Only then materialise a verified explicit GRANT/REVOKE in existing PostgreSQL `CustomerPhone`. A recoverable REVOKE is applied even if no outbound recovery record/message will be created. A normal completed checkout contributes no new SQL decision. No receipt means no new decision: reuse prior verified SQL consent only if current customer/recipient binding and STOP permit it.
6. Recheck current SQL stored consent and STOP at every proactive final outbound send, including initial outreach, unsent retry, follow-up, multipart; no extra Redis check. A valid Cart A initial message can remain, but after recoverable Cart B REVOKE commits, no new unsolicited Cart A follow-up may start. Existing customer-initiated AI/human service replies remain eligible under their separate policies. Preserve existing credit and ARCH-076 sender guarantees.
7. **Existing-schema idempotency / accepted delayed replay:** Reuse current per-checkout BullMQ/recovery identity, durable state checks where they actually demonstrate prior application, SQL transaction/revision/STOP protection and existing outbound idempotency. Do not reapply a consent decision **when existing durable evidence proves that same checkout's decision already took effect**; do not assume a recoverable REVOKE created `CheckoutRecovery`. If no durable evidence proves the decision already materialised, process the independently recoverable checkout via the ordinary existing consent transaction. The architect and developer explicitly accept that an exceptionally late older checkout can therefore overwrite a newer stored consent decision. This stateless v1 architecture **does not guarantee cross-checkout exactly-once or monotonic checkout-order consent**. No new SQL checkpoint, table, migration, Redis consent ledger, global lock, or `MATERIALISATION_IDEMPOTENCY_BLOCKER` solely for that accepted limitation. Existing STOP, final-send SQL and recovery admission checks are not relaxed.

## Non-Plus current-cart verified display — S003 architect correction (18 November 2026)

The only current cart selection is `attributes.moda_wa_consent_v1`. **A pre-existing receipt is not equivalent to an unchecked default.** On cart render, the storefront must obtain a bounded, server-authenticated decision for the receipt already read from its current `/cart.js` response. A valid signed `G` displays checked; `R` displays unchecked; neither produces a new receipt or changes PostgreSQL. If there is no attribute, the existing returning-customer SQL status is the display fallback. A nonempty but invalid/unverifiable receipt hides only the Moda checkbox; do not silently display false or fall back to stale SQL permission.

S003 is expressly authorised to add **one read-only route** to the existing Shopify-owned App Proxy handler: storefront `POST /apps/moda-consent/cart/verify` -> application `POST /shopify/consent/cart/verify`. Request JSON has exactly `cartToken` and `receipt`. Use the *existing* signed App Proxy shop/customer, timestamp freshness, shop scope and origin validation. Call S002's existing `verifyConsentReceipt` with `kind:"c"`, authenticated shop and customer, and the current cart token. Return exactly `{source:"verified_receipt",decision:"GRANT"|"REVOKE"}` on verified success, `Cache-Control:no-store`; return a bounded error and no raw receipt/claims otherwise. Do not add HMAC, Redis choice storage, separate keyrings or any SQL write on verification. Preserve the existing accepted same-checkout replay limitation.

**Merchant-customised App Proxy root for S003:** Shopify allows the installed merchant to customise the storefront App Proxy `prefix` and `subpath`, so S003 must not hard-code `/apps/moda-consent` for all storefronts. Its cart Theme App Block exposes exactly one text setting, `app_proxy_root` (default `/apps/moda-consent`); the frontend validates a supported Shopify prefix (`a`, `apps`, `community`, `tools`) and one safe subpath, then derives status/receipt/verify URLs from that root on the same origin. If the setting is invalid or stale, hide only Moda's block; never send the receipt to another origin or block checkout. Shopify does not expose the merchant-customised path through the existing authenticated GraphQL checkout query; S005 owns accurate merchant guidance for keeping the App Block value in sync with the actual installed proxy configuration. No proxy-discovery service, Redis key or extra consent endpoint is authorised.

Shopify theme editor can replace the block section without a full page reload. S003's front-end initialiser must handle the section-load event without duplicating handlers or recording consent on render. Merchant activation metafield setting/published-theme confirmation remains SHOPIFY-005's responsibility; real signed-receipt cart-to-webhook-to-GraphQL and Plus certification remains downstream and must not be falsely claimed by unit tests.
