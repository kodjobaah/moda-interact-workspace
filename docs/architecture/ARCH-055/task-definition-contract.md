2. Persisted fields specify Prisma name/type/native type, nullable/default policy, SQL schema/table/type, affected indexes/constraints and legacy/backfill behavior. Expected executable SQL is provided where Database work is selected.
3. Local interfaces specify exported symbol, argument/return fields and who owns caller error mapping; database errors preserve the original cause. Public/Shared DTOs are unchanged unless a specifically identified OpenAPI documentation correction is authorised.
4. Mutation steps name tenant/revision/generation predicates, exact-one return/count checks, isolation/lock order and transaction/external-I/O boundary. No prior SELECT followed by an unconditional ID-only UPDATE is presented as a concurrency check.
5. Test rows name fixtures/interleavings and observable results, plus exact file/runner registration. Required unavailable checks remain unchecked and block acceptance. Existing helper models/mocks do not prove real migrated lock behavior.
6. Validation lists real baseline commands or clearly labelled new scripts, default migration target, no hosted resources, cleanup and evidence. Optional experiments retain baseline behavior and return findings, not autonomous architecture changes.
7. Stop at review; do not accept own task, modify indexes/other task status or begin enabled tasks.

## Forward-only migration policy

Every schema/guard correction is implemented in a NEW ordered `prisma/migrations/<named-id>/migration.sql` file. Existing applied migration bytes and `_prisma_migrations` records remain unchanged. Do not use reset/db-push/squash/repair-marking or an automatic down script. A later defect uses another named forward corrective migration after architectural definition.

Forward-only does not forbid correcting an installed SQL function or CHECK. DATABASE-001 explicitly replaces one function and one CHECK in a new transactional script; no other trigger removal or constraint weakening is implied. The separate claim-key metadata backfill temporarily disables one named existing trigger only under ACCESS EXCLUSIVE in the same transaction; it restores the original function/enabled state and has rollback tests. No blanket trigger-disable or replication-role change is permitted.

Migration1 corrects FAILED terminalisation only; API owns new current-Shop/principal policy. Migration2 adds one nullable command metadata column and preserves historical claim identity. Migration3 adds one nullable purpose column and one original-intake partial unique index with a fail-closed duplicate-history preflight. No new business-policy triggers, purpose immutability/nonblank checks or key=command.id SQL policy guards are created.

If a previously supplied ARCH-055 migration has already run, these proposed names cannot be reused with different SQL. Stop and collect names/checksums/current state; a new forward reconciliation must be authored. A documentation patch is not permission to rewrite executed history.

## Repeatable API evidence protocol — revision 3

This section clarifies the existing before/after evidence requirement for API-001 through API-009; it creates no task, production instrumentation, standalone benchmark framework, migration or discretionary optimisation. Canonical edit maps still decide which changes are mandatory. Attach the measurements to the owning task's existing Completion Report and its named integration suites. ### Fixed comparison procedure

- **Versions:** record the implementation repository's task-start SHA, candidate SHA, accepted Database pin/migration hashes, Node/Prisma versions, fixture/test path and exact existing validation command. The comparison baseline is that task's prepared starting code, not an arbitrary later branch or the whole initiative's first snapshot. Run baseline and candidate separately with identical disposable PostgreSQL 17 + pgvector schema and seeded data. Where accepted earlier migrations require compatibility setup, apply the SAME setup to both and record it; do not rewrite a migration or invent a passing old-code run. An actual baseline incompatibility is reported with the failed command and blocks a claimed numeric before/after comparison, not the correctness test.
- **Runs:** for each profile, perform two discarded warm-up executions and five recorded executions per version, one operation at a time. Restore that profile's database rows/state before EACH execution, outside the measurement window. Do not let a CREATE become a replay or let counters/preferences accumulate across samples. Reuse a warmed client within one version; close it at runner shutdown. Required race scenarios run separately with explicit barriers, not averaged into success-path timings.
- **Boundary:** measure the named service method, excluding HTTP authentication, fixture setup and post-test assertions unless a profile explicitly tests real HTTP (API-009). Include service-owned configuration reads, transactions and post-commit projections, listing their phases separately. Use in-process deterministic provider/R2/queue ports for non-dependency profiles; record invocation counts and never contact real services. API-004 configuration-pool tests must use real production database configuration composition, not a constant stub.
- **Inputs:** use fixed fixture IDs/sort timestamps through the existing fixture factories, stable ordering and `2026-11-02T12:00:00.000Z` for injectable business clocks. For DB-clock expiry tests, seed validity relative to the actual test DB clock instead; those barrier schedules are not throughput samples. Do not monkeypatch process/global time or change database timezone to manufacture equivalent results.
- **Record per execution:** logical client calls, actual emitted SQL by normalised statement shape, separate BEGIN/isolation/COMMIT/ROLLBACK count, returned row counts, affected target-row counts verified by operation result or persisted snapshots, no-op timestamp assertions, operation/transaction elapsed milliseconds, retry count and external-port invocations. Trigger-internal work and wire bytes are recorded only when actually observable; otherwise say `not measured`. Do not label JSON-length estimates as network bytes or transaction-entry time as pure pool wait. Use existing query logging/approved instrumentation and test-local counters; never log parameter secrets/customer bodies or add a generic production metric family.
- **Acceptance:** exact output/state and the task's chosen query/row-shape change must hold for all five samples. Keep source-level/client-call targets distinct from emitted SQL. Report raw samples and min/median/max duration as descriptive evidence only; five samples establish neither production p95/p99 nor capacity. There is no invented latency-percentage gate. Explain any additional mandatory authorization calls instead of concealing them in an optimisation total. Missing visibility is explicit, not a guessed zero.
