# ARCH-077 — Shopify-owned WhatsApp checkout consent

> **ARCHITECT AUTHORISATION — definition-only, 17 November 2026.** The real-browser cart-to-checkout **correlation evidence** and the documented v1 marker/event/Redis contract are accepted for implementation planning. SHOPIFY-001 is recorded `completed` as contract/evidence work; SHARED-001 is `ready` for implementation. Dependent tasks follow their `depends_on` edges and may start as prerequisites finish. Guest identity and crash-safe SQL behaviour remain **runtime acceptance tests**, not requests to repeat the completed marker experiment. This document deploys no runtime change.

## Purpose and ownership

In a real Shopify abandoned-checkout test, the checkout had a Shopify customer ID and billing/shipping phones but `customer.phone` and `customer.defaultPhoneNumber` were null. Background found the checkout and returned `deferred-no-recipient`. ARCH-077 replaces the Shopify-native WhatsApp marketing-consent dependency with **Moda's own Shopify checkbox**, without changing WooCommerce or requiring Shopify Messaging.

- `moda-interact` owns Shopify's consent capture, authenticated status reads, two Shopify extension presentations and temporary Redis writes; `moda-interact-background` owns cart-to-checkout association, recoverability, recipient selection, PostgreSQL materialisation and outreach admission.
- `moda-interact-api` is WooCommerce-facing and `moda-interact-woocommerce` stays unchanged. No new standalone Shopify API application.
- **No database migration, schema/enum/table change.** Existing `commerce.Customer`, `commerce.CustomerPhone`, revisions and STOP protection are reused. The existing enum value **`SHOPIFY_NATIVE` is the approved database identifier for Moda's Shopify checkbox consent** in this initiative; it does **not** require a Shopify-native WhatsApp marketing API observation. Obsolete provider reads, projection/sync writers and webhook processing must be retired in B002/S006. Do not use the WooCommerce-installation-bound `commerce.WhatsAppConsentEvidence` table for Shopify.
- The customer-facing checkbox wording is **exactly** `Send me WhatsApp shopping updates, reminders and offers.` Reuse its meaning in Shopify-owned translations; do not import WooCommerce implementation or alter the wording. Permission covers checkout-recovery shopping updates, reminders and offers from the identified merchant, not unrelated campaigns or other merchants.
- Existing merchant-defined inactivity delay, Shopify abandoned-checkout verification retries, order/payment cancellation, STOP, billing/credit compensation, moderation, two-proactive-outreach limit, human/AI communication controls and ARCH-076 sender routing remain in force.

## Consent policy — customer scope, checkout correlation

- Consent is **merchant-scoped customer permission**, valid for future eligible abandoned checkouts once recorded in PostgreSQL, not merely permission for the first basket. Cart/checkout tokens provide a verified path from the explicit selection to the recovery being processed; they are not lasting customer identities.
- For the **same cart/checkout**, the latest successfully acknowledged explicit checkbox action is the temporary selection shown to the shopper. **Across distinct checkouts**, only successfully materialised choices from independently recoverable checkouts change merchant/customer permission; Cart B's later successful materialisation supersedes Cart A's earlier successful materialisation. A duplicate/replayed job for A is not a new decision. Neither cart creation time nor an unchecked default can change persistent permission. Never use client-side action ordering as an excuse to write PostgreSQL before recoverability.
- **At checkbox interaction:** record only a temporary GRANT/REVOKE choice in a separate Shopify consent Redis namespace. No `Customer`, `CustomerPhone`, consent revision, STOP or SQL evidence change occurs, **including when a returning customer unchecks an already checked box**.
- **At eligible abandonment:** Background retrieves the authoritative Shopify abandoned checkout; resolves the verified customer and recipient; obtains the latest verified temporary choice (if any); and applies that choice to existing PostgreSQL consent state **only when the checkout becomes recoverable**. If there is no explicit choice, it may reuse already verified PostgreSQL consent for that shop/customer/recipient. STOP overrides any grant.
- **At normal completion or definitive ineligibility:** no PostgreSQL consent update occurs. Temporary Redis consent is cleaned up through the existing recovery lifecycle. A returning customer's next new cart reads the still-current PostgreSQL permission again. This is the approved deferred-grant/deferred-withdrawal business rule; no click-time SQL withdrawal exception is part of ARCH-077.
- PostgreSQL is authoritative **after materialisation** for initial proactive outreach, re-entries, retries, proactive follow-ups and the existing final SQL dispatch fence. Redis is not a permanent customer-preference database and is not queried on every later send. Do not introduce a Redis/PostgreSQL distributed final-dispatch lock.

## Frozen outreach versus ongoing-conversation policy — ARCH-077 (17 November decision)

**This policy is mandatory and supersedes any older wording in S001/S002/B001/B002/SYSTEM-TEST that might imply immediate withdrawal, click-time suppression, or denial of all messages in an already-open conversation.** It is the requested *deferred-both-decisions* product rule; any regulatory assessment is separate and must not be silently implemented by an agent as a different rule.

1. **Choice only:** An explicit GRANT or REVOKE is recorded in temporary shop/cart or authenticated Plus checkout Redis records at checkbox interaction. A checked/unchecked display, ordinary webhook and cart marker never create a decision. The exact checkbox copy stays `Send me WhatsApp shopping updates, reminders and offers.` Do **not** change its text, defaults or locale semantics to explain the lifecycle.
2. **No pre-recovery effect:** Neither temporary GRANT nor temporary REVOKE changes PostgreSQL, `CustomerPhone` revisions, the effective permission for *other* recoveries, scheduled proactive messages, or a separate opt-out register. Specifically, an existing GRANTED customer selecting REVOKE in Cart B has **no new suppression** until B independently becomes recoverable. Do not add an immediate Redis suppression gate, SQL withdrawal, silent STOP or callback that changes outreach admission on checkbox interaction.
3. **Recoverable means pre-consent recoverable:** B002 first establishes an actual abandoned, unpaid, not-completed, merchant-delay-matured checkout from authoritative Shopify state using all existing eligibility guards, **without requiring GRANTED consent or creating `CheckoutRecovery`**. Then it resolves shop/customer/attributable phone and the verified latest explicit cart/checkout selection. This permits B's REVOKE to materialise despite B being ineligible for messaging. If recipient/customer cannot be verified, defer/fail closed; do not invent a phone or record a customer-level decision.
4. **Materialise:** For a *verified, recoverable* checkout with an explicit choice, perform the existing customer/active `CustomerPhone` GRANT/REVOKE transaction, proper shop/phone/STOP constraints, purpose and incremented consent revision/sequence; acknowledge success only after PostgreSQL commits. A recoverable checkout with no explicit new choice does not create a consent decision and may reuse existing verified SQL permission. A checkout completed/paid or definitively ineligible before recoverability contributes **no** SQL decision, even if it contained REVOKE; discard its temporary choice through normal terminal cleanup.
5. **Across recoveries:** Distinct checkouts are sequential *decision opportunities*, not simultaneous checkout screens. Cart A materialises GRANTED and sends its initial outreach. Later Cart B materialises REVOKED. From that successful B commit onward, no **new proactive** initial outreach, proactive retry, scheduled follow-up, multipart promotional send or other unsolicited outreach may start for A, B or another checkout in the same merchant/customer/recipient permission scope. Never recall a provider-accepted message or retroactively invalidate A's already delivered message. A stale/retried A materialisation must never regrant after B; S001/B002 must prove one-time materialisation and crash/retry ordering before rollout.
6. **Separate conversation admission:** Cart A's existing conversation remains open. If the customer initiates a message or replies, the existing AI/human service-reply path may answer under WhatsApp's customer-service window, existing message moderation, routing and STOP policies. A service-window being open is **not** permission to send a proactive follow-up. Customer-service replies do **not** regrant promotional consent. Do not modify conversation records/status or add a broad `REVOKED => all outbound blocked` guard.
7. **Immediate STOP unchanged:** A customer-issued STOP follows the existing independent shop-scoped suppression pathway immediately; it is not a checkbox REVOKE and must not be deferred. Existing inbound routing, moderation and customer-service policies decide how to process that inbound STOP.

**Mandatory scenario matrix (no alternative interpretation):** A GRANT selected -> temporary; A recoverable -> SQL GRANTED -> A initial outreach; B REVOKE selected -> temporary only -> A permissions still per SQL; B *paid* -> discard B REVOKE, SQL stays GRANTED; alternatively B *recoverable* -> SQL REVOKED, B initial outreach denied, A unsent proactive follow-up denied, A already delivered initial outreach unchanged, customer-initiated AI/human reply in A remains permitted by existing conversation rules; C becomes recoverable without explicit choice -> no new outreach while SQL REVOKED; C selected GRANT and becomes recoverable -> SQL GRANTED may allow new outreach subject to existing guards. No checkbox action itself sends a message or creates credits.

## Presentation and returning customer

**A — Standard-plan cart page:** A merchant-enabled Shopify Theme App Extension App Block, added/saved through Shopify's theme editor, reads the current Ajax cart token and submits only deliberate changes to the authenticated Moda Shopify backend. An authenticated `checkouts/create` or `checkouts/update` event provides a checkout token and the validated, shop-scoped correlation-marker digest for B001's association; direct cart-token equality is not required. Support consent before/after the relevant webhooks without guessing identity from email, phone, matching products or timestamps. The Shopify settings UI provides a verified cart-template activation deep link/status; installed or previewed is not automatically published/active.

**A — confirmed correlation implementation boundary:** The cart App Block calls the Shopify app's authenticated App Proxy to obtain a server-issued, cryptographically random, cart-scoped marker and writes that exact value as the Shopify cart attribute `moda_cart_correlation_v1` using the locale-aware Ajax `cart/update.js` endpoint. S002 owns generation and an atomic cart/marker index in separate Redis keys; S003 owns the cart attribute read-back. The marker is **not consent**, not a customer identity, and not an authentication credential. An unacknowledged marker write never enables the Moda checkbox. Shopify authenticated ingress extracts the attribute from the checkout webhook's `note_attributes`, validates it and forwards **only the temporary opaque marker and a small classification** in the existing strict Shared V2/V3 checkout event; B001 resolves that marker against S002's shop-scoped Redis binding; it never accepts a client-provided cart identity as the recovered checkout's authority. The existing `checkout.cart_token` may agree or differ and cannot be the sole linkage prerequisite. Guest checkout ownership must be established by the **fixed B001/B002 decision gate below**; the marker alone does not supply it.

**E — Shopify Plus checkout:** A distinct Checkout UI Extension at the supported `purchase.checkout.contact.render-after` target uses Shopify's signed extension context and verified checkout token to write directly to checkout-scoped temporary Redis consent. When both extensions are enabled, display the latest authenticated, accepted explicit choice for the current checkout/cart before falling back to previously verified PostgreSQL permission; display alone never records a new grant.

**Returning authenticated customer, new cart:** Identify the customer by verified Shopify customer identity within the merchant scope, not by the new cart token. Read their already materialised current `CustomerPhone` consent and no-contact status **from PostgreSQL through S002**. A verified GRANTED decision displays checked; REVOKED/UNKNOWN/ambiguous/unavailable evidence cannot be claimed granted. An explicit change is temporarily recorded on the current cart/checkout and only materialised if it becomes recoverable. Guests with a new unrelated cart do not inherit previous permission from a matching phone or email.

**Shopper failure behaviour:** If Moda's status/write endpoint or Redis is unavailable, both extensions fail **silently**: no error banners, toasts, prompts or blocking payment/navigation. Hide only Moda's control when its initial status cannot be verified; never visually claim an unacknowledged action succeeded. The server preserves original useful underlying errors with required secret/PII redaction.

## Checkout marker transport — existing strict Shared queue schema

The 13 November source snapshot confirms `app/services/webhooks/checkout-normalization.ts` currently forwards only checkout token, cart token, checkout created time and abandoned URL; it drops `note_attributes`. Shared `CheckoutCreatedPayloadV2Schema` and `CheckoutUpdatedPayloadV3Schema` are strict and currently have no marker field. **B001 cannot read the observed marker from existing checkout queue jobs without an explicit compatible Shared contract change.** ARCH-077-SHARED-001 adds a narrowly scoped, optional marker+observation-status field to those existing versions; S002 maps only the specific marker from authenticated webhook payloads into those fields. This is not a new queue, schema version or broad webhook-body forwarding. Both applications must pin the new Shared package before the Shopify producer emits the new fields. No native consent integration or recovery queue lifecycle changes are authorised by this boundary.

## Recipient and verified recovery

At eligible abandoned-checkout maturity, B002 reads the existing authoritative Shopify lookup and considers contact candidates in this priority: **customer phone → billing phone → shipping phone**. An invalid or absent higher-priority number may fall back to the next valid, attributable number. Different values across these fields are not automatically ambiguous; a known third-party shipping contact must not be treated as the consenting customer merely because the number appears on the address. Use the published Shared canonical phone contract, the correct shop/customer identity, and preserve any pre-existing STOP/no-contact history on formatting/phone changes. No additional cart-page phone field is required.

`customer.phone = null` with matching billing/shipping phone is the observed regression case. Neither finding a number nor discovering an abandoned checkout manufactures consent. The old Shopify `defaultPhoneNumber.whatsAppMarketingConsent` API is not consulted.

## Fixed implementation boundaries and conditional stop gates

- **Identity (frozen no-extra-auth design):** Signed App Proxy authenticates the *shop*, not the guest. The public Ajax cart token and shopper-writable marker are only **temporary locators**, not verified user identity. S002 accepts a *temporary, side-effect-free* checkbox choice solely against an atomically prepared `{shopId,cartDigest,marker}` record after signed App Proxy verification and revision/idempotency checking; it cannot materialise consent, schedule marketing or accept a client-asserted `customerId` at click (a signed-proxy verified logged-in Shopify ID may be recorded for later B002 comparison). B001/B002 must require **both** (i) a validated, nonconflicting shop-scoped marker from an authenticated Shopify checkout webhook and (ii) one of the following independently checkable bindings before materialisation: **GUEST** — the webhook `cart_token` canonical digest exactly equals the original cart digest; **AUTHENTICATED** — a Shopify `logged_in_customer_id` verified by the signed App Proxy *at the accepted action* is stored in the cart choice and equals the authoritative Shopify checkout customer ID. The marker alone, a client-provided customer ID, phone/email match or basket similarity never passes. If neither binding passes, return `DEFER_IDENTITY_OR_RECIPIENT` and perform no SQL or send. This intentionally makes the observed mismatched-cart guest pathway fail closed while allowing matching-token guests and verified same-customer authenticated transitions; agents must not invent another cookie/JWT/auth framework. Plus continues to require its independently verified signed extension session/checkout context. Actual supported-plan behavior and adversarial failures are tested before rollout, not a preliminary block on implementation.
- **Minimal existing-event transport:** Add only optional `cartCorrelationMarker` (46-character `m1_` random value) and `cartCorrelationMarkerStatus` (`PRESENT|ABSENT|INVALID|AMBIGUOUS`) to the existing Shopify checkout V2/V3 event contracts. The marker is already exposed as a shopper-writable Shopify cart attribute and contains **no PII or consent decision**. Carrying it through the existing bounded checkout-event queue does not create a new permission source, queue, encryption/HMAC key or long-lived record. `PRESENT` requires the validated marker; other states omit it; legacy events omit both fields and are `NOT_OBSERVED`. Do not print the marker in logs or retain it beyond normal queue/Redis expiry.
- **Persistence/idempotence release gate (implementation may begin):** With no new SQL table/column authorised, B002 must demonstrate that a distinct eligible checkout choice is applied **at most once** across worker retries, process crashes between SQL commit and Redis cleanup, and concurrent recoveries. PostgreSQL consent/STOP revisions and current permission remain authoritative, with a short existing SQL final-send fence. The Redis association/consumed state is temporary coordination, **not** a substitute for atomic durable applied-decision evidence. If the current schema cannot establish crash-safe idempotence and later materialisation precedence, B002 must report the exact missing evidence to the architect and halt its implementation before persistent consent writes; they may not invent a schema, backdate a decision, silently reapply A, or relax the rule.
- **Proactive-versus-reactive gate:** Only customer-unsolicited recovery outreach (including follow-ups and provider retries not yet accepted) is checked against current merchant/customer/recipient `CustomerPhone` consent. AI/human replies following actual customer inbound use the existing independent conversation admission and 24-hour policy; opening a service window does not convert a scheduled outreach into a reply. STOP and provider-specific guards retain their current independent operation.

## Redis ownership, ordering and cleanup

- S001 must freeze **exact, versioned and independently namespaced** temporary cart choice, checkout choice and verified cart-to-checkout association records, keyed with scoped encoded/token-digest identities, including replay handling, accepted-action ordering, expiry and cross-repository test vectors. **Do not create permanent Redis customer-preference or consent-history mirrors.** Store only bounded evidence required to process the active cart/checkout.
- Consent writes are acknowledged only after atomic Redis success. Duplicate actions are idempotent, conflicting replays fail and older accepted actions must not be replayed over later choices. B001 does not grant permission on a webhook.
- Temporary consent survives normal candidate activity, merchant-configured maturity, bounded abandoned-checkout visibility retries and any necessary recoverability/materialisation retry. Cleanup occurs only after a successful B002 materialisation or after the cart/checkout has definitively completed or become ineligible. An active cart with no checkout has separately bounded retention. No premature cleanup on theme navigation, job-index deletion or frontend unload.
- Consent keys are **not** the existing `pending-recovery:index:checkout:*`, `pending-recovery:index:cart:*`, `pending-recovery:index:shop:*`, `pending-recovery:lock:*`, `pending-recovery:order-completed:*` or BullMQ job/payload keys. Those owners retain their exact values, TTLs, rescheduling and deletion semantics. No `KEYS` scans, `FLUSH*`, global Redis policy changes or new consent queue/scheduler without separate approval.
- Redis outage, lost evidence or indeterminate association must never manufacture permission. Existing PostgreSQL consent may be used only when the absence of a pending choice is **verified** under the approved S001/B002 read contract; a failed Redis read must not be treated as an empty choice.

## Persistent consent and final dispatch

- B002 performs any required `Customer`/`CustomerPhone` mutation **only at recoverable checkout maturity**, using the existing `SHOPIFY_NATIVE`, `WHATSAPP_CHECKOUT_RECOVERY`, verified timestamps, monotonic decision sequence/consent revisions and STOP/no-contact columns. A newer accepted checkout decision cannot be undone by an older delayed worker. Newer explicit GRANT can follow REVOKE without clearing STOP.
- Following materialisation, the existing `RecoveryStoredConsentService`, `recovery-runtime-eligibility.service.ts`, `checkFinalStoredRecoveryConsent`, multipart and outbound admission paths read current PostgreSQL consent and enforce the short final SQL fence. No Redis read inside that transaction; do not disable the final gate. Customer-initiated replies and WooCommerce's separately owned admission policy remain unchanged.
- The obsolete Shopify native-consent GraphQL provider, webhooks, job publisher, sync processor and projection behavior are removed through B002/S006. **Preproduction:** no legacy-job adapter or data compatibility is required; any environment cleanup must be scoped and must not flush the shared checkout/cart/order queues or unrelated customer/STOP data.
- Existing Shopify consent table limitations remain explicit: `CustomerPhone` is current durable permission, whereas the Woo-bound `WhatsAppConsentEvidence` cannot serve as Shopify disclosure-event history. ARCH-077 forbids new tables; do not claim a complete immutable Shopify SQL evidence history that does not exist. S001/B002 must specify what bounded Redis evidence is available at materialisation and report any audit/proof blocker rather than bypass the approved storage boundaries.
