## C. Conversational host pipeline

Implement the same order in BACKGROUND-001 and COMMERCE-001:

Standalone Background owner is Conversation.shopId, recovery-linked owner CheckoutRecovery.shopId; if both exist and differ refuse before model/provider calls. 3. Record validated successful search/get product observations; use the existing authoritative model/tool ledger and total deadline. Malformed canonical output => host failure. Correctable NOT_FOUND/INVALID_INPUT still consume budget and remain visible; DENIED/outage referral semantics remain published runner rules. No automatic budget increase.
4. Read final selection. Ordinary productOptionSelections uses verifyCommerceOptionFacts and PRODUCT_OPTIONS. New productDetailSelections uses verifyCommerceProductFacts and PRODUCT_DETAILS. For each selected exact pair perform one authorized fresh get_product after model completion, deduplicating within this verification phase only. A prior search is not a substitute for this fresh verification. For recommendation products/discount/shipping retain existing Background revalidation rules, including policy refresh, sale/offer evidence, purchasability, safe same-shop URLs and required variant identity. Studio must implement equivalent read-only verification rather than skip it.
5. If there is no remaining call/time allowance refuse with BUDGET_EXHAUSTED/DEADLINE at presentation.verify, not a truncated or invented answer. 6. Build strict host-verified presentation and call composer once. Refer-to-store safety has priority over merchandising. 8. Persist references only from successful authorized observations using Shared reducer; failed/stale/cancelled or presentation-refused turns do not publish context updates. Do not publish context merely because the runner succeeded if host verification/composition failed. Delivery failure alone does not invalidate already verified reference facts, but must not trigger a second context update or extra send.

## D. Database write algorithm

Follow exact Prisma/SQL in DATABASE-001. Validate all JSON through Shared before read/write; row identity and payload identity/version equal. Enforce both JSON UTF8 and pg_column_size limits. Read invalid/expired payload as logged empty reference data. Staleness after read never becomes permission.

Background repository exports read({shopId,conversationId,now}) => context|null and write({shopId,conversationId,expectedInboundVersion,context,now}) => WRITTEN|UNCHANGED|STALE|CONFLICT|SKIPPED. Use dedicated short transaction after successful presentation; lock canonical Conversation FOR UPDATE, read checkoutRecovery owner if present in same transaction, verify expected version and owner. Missing/deleted/wrong owner => STALE. Existing source version>expected=>STALE; same version+canonical-JSON equal=>UNCHANGED without extending expiry; same version+different=>CONFLICT. Older existing row=>update with predicate conversationId/shopId/revision and revision+1, exactly one affected row else CONFLICT. Missing row=>insert revision1; unique collision=>CONFLICT, no overwrite/retry. Write sourceInboundVersion=expected; expiresAt=now+24h. No lock across model/provider/composition I/O. Technical DB failure logs SKIPPED and does not retry sending; caller's original send fence still applies. Canonical serialization must use sorted object keys for equality, never raw JSON property-order equality. Lazy expired-row cleanup may delete only that conversation/tenant row in a short transaction; no global purge worker.

## F. Definition-review rule

Every pending task must list its owned paths, contract sections, accepted artifact/migration prerequisites, test command/evidence requirements and deliberate behavior changes. ## G. Deployment and version compatibility gate

Additive optional fields preserve old data parsing by new consumers; they do not prove that an old strict output schema accepts newly emitted fields. No rolling-deployment compatibility claim follows automatically. Pending tasks validate in a disposable environment with matching published descriptors, new Shared artifact and all updated consumers. No production deployment/activation is authorized here. Before a later production rollout, deploy readers/hosts that accept new optional fields first, verify MCP and default profile compiled schemas, and activate matching new immutable descriptors/profile together under the existing publication mechanism; never mutate old published output schemas or widen unknown properties. If a provider runtime cannot honor the active old descriptor, keep that release inactive until the coordinated rollout gate is satisfied. System tests must demonstrate old stored products/context still load and new active descriptor/profile passes actual current outputs. Version/activation mismatch is a typed validation refusal, not fabricated empty catalogue data.
